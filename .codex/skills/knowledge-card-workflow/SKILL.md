# 知识库选题与逐张制卡

在 `knowledge-base/` 内工作。先遵循该目录的 `AGENTS.md` 和 [维护手册](../../../knowledge-base/README.md)；涉及 Java 基础时，以对应主题 README 中的范围和固定版本为准。`knowledge-base/references/` 是原始资料目录，不进入知识库导入范围。实际落卡时同时遵循 [card-writing](../../../knowledge-base/skills/card-writing/SKILL.md)。

## 候选清单：先供用户审题

1. 根据用户给出的大纲确认主题范围、版本和目标读者。只检索相关的 `references/` 资料、现有卡片和主题 README；不要把历史调研记录当作每次制卡的必读材料。若本次需要创建或调整目录，按知识库规则先维护 `outline.json` 并预览。
2. 把资料里的相近题目转成可独立评价的候选问题。检查现有卡片与候选项之间的重复、包含和前后置关系，提出新建、扩充已有卡、合并或暂缓的建议；不照搬来源题目，也不为覆盖资料目录而凑卡片数量。
3. 交付按大纲分组的候选清单。每项写明候选问题、建议处理与理由、目标节点、相关的已有卡片，以及**直接指向源文档具体文件或章节的可点击引用**。GitHub 资料使用主题 README 约定的固定提交链接，尽量定位到标题或行；不要只给仓库首页、资料名称或本地路径。可附本地路径便于工作区检索，但不能用它代替原文链接。没有可访问的原文链接时明确标为“仅本地资料”，不要编造链接。多个候选共用资料时，仍须让用户从每个候选项定位到对应原文。
4. 区分“选题线索”和“事实依据”：候选清单中的第三方文章说明问题从何而来，不表示其所有结论已获核验。标出需要在写卡时核对的版本差异、实现细节或可能有争议的说法。清单过长或需要跨会话审核时，可把它保存为 `knowledge-base/references/` 下的非导入 Markdown，并在回复中给出链接。

候选清单提交用户审核后，再按其保留、合并、改题、排序意见定稿。用户尚未审核选题时，不批量创建正式卡片。

## 逐张制作：每张都可单独审核

按审核后的顺序一次制作一张。针对该卡阅读已列出的相关资料；对影响结论的不确定事实、版本行为和框架实例，按需核对当前问题对应的官方规范、API 文档或固定版本源码。独立组织答案，不复制第三方正文；在卡片的参考资料中列出实际用于支撑关键结论的具体原文链接，框架实例给出对应官方文档或固定版本源码。

每张完成后交付卡片文件链接、所用主要来源和需要用户判断的取舍，等待这张卡的审阅意见，再进入下一张。若制作时发现原选题需要拆分、合并或改归属，先更新候选建议并让用户审核该变化。日常制卡不主动运行校验或导入；仅在用户要求或当前会话已有相应授权时执行。
