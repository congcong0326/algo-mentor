# Java 与计算机知识内容产品方向

设计日期：2026-09-14

> 2026-09-15 产品方向修订：第一阶段以共享知识大纲和问题卡为核心，概览文章改为按需生成、人工批准的可选内容。本文保留早期内容模型讨论；研发实施以 [`docs/product-planning/knowledge-outline-card-v1-design.md`](product-planning/knowledge-outline-card-v1-design.md) 为准。

需求修订：总览定位为当前层级的介绍文档，帮助用户建立整体认识；内容导航由目录和页面结构承担。

## 我们要做什么

我们要做的不是一个把面试题和答案堆在一起的资料库，而是一套帮助用户**理解知识、形成联系、练习表达并持续复习**的学习工具。

用户可以从一篇主题总览开始，了解这一层级是什么、为什么包含这些内容、各部分有什么关系，以及哪些内容最重要；然后通过页面中的子主题或卡片列表进入具体知识点，尝试自己回答，查看解释，完成配套选择题，并在之后通过复习队列再次回忆。

有基础的用户可以跳过总览，直接看问题卡。没有基础的用户可以沿着总览和前置知识逐步学习。两类用户使用的是同一套内容，只是入口和学习路径不同。

## 内容如何组织

内容由总览文章和问题卡组成，通过总览文章树、页面中的内容列表以及卡片关联组织起来。总览正文介绍知识背景，目录表达层级，卡片展开具体知识点。

### 知识导航树

用户看到的主导航是一棵由总览文章组成的树，用来帮助用户定位知识：

```text
Java
├── 基础总览
├── 集合总览
├── 并发总览
├── JVM 总览
└── Spring 总览
```

目录负责“这部分知识放在哪里”，页面中的子主题和卡片列表负责进入具体内容。层级和列表顺序独立于总览正文维护，不要求文章用链接复述目录。领域和标签可以用于筛选和推荐，但首版不额外维护一套与总览树重复的主题树。

### 总览文章

总览文章是当前层级的介绍文档。读完后，用户应该对这个主题有大概的认识，知道为什么要了解这些内容、理解时应抓住什么。它主要解释：

- **这是什么**：讨论的对象、范围，以及在更大知识领域中的作用；
- **为什么需要它**：要解决什么问题，为什么形成这些概念、机制或分类；
- **整体如何理解**：主要部分各自承担什么职责，彼此有什么关系；
- **哪些内容重要**：优先建立哪些认识，哪些属于后续深入的细节，以及这样区分的原因。

这些是写作目标，不要求每篇采用相同的小标题。可以通过简短例子、图示或必要的流程说明帮助理解，不要求每篇都围绕一次操作展开。介绍应解释分类和机制存在的原因，不能只把目录标题改写成段落。

总览正文默认独立成文，不要求总览之间相互引用，也不要求链接或介绍下一级的问题卡。即使下一级全部是卡片，正文仍只介绍理解这个主题所需的背景、整体结构和重点。用户看到卡片列表时，才进一步明确有哪些具体知识点需要掌握。

主题概念可以在多个层级按各自深度自然出现，例如集合总览可以解释相等性为何影响去重，但无需在正文跳转到另一篇文章。来源引用用于事实追溯，可以保存在来源记录中；它与正文中的学习导航是不同职责。

总览文章之间也可以建立主从关系。例如：

```text
Java 集合总览
├── List 总览
│   └── ArrayList 总览
├── Set 总览
└── Map 总览
    ├── HashMap 总览
    └── ConcurrentHashMap 总览
```

这样 `HashMap` 位于 `Java 集合 → Map → HashMap` 这条路径上。主从关系由导航树表达；父级介绍更大范围的分类与重点，子级介绍当前主题的背景与核心认识。用户可以通过目录进入任意层级，不必顺着文章内链逐篇阅读。

例如集合总览介绍为什么需要不同的数据组织方式，Map 总览介绍键值映射的用途，HashMap 总览介绍哈希查找的基本思想和使用时的重要约束。三篇文章可以各自完整阅读，详细实现和边界问题由卡片展开。

### 总览的验收标准

审核一篇总览时，主要看以下结果：

- 只看正文，能否说清这个主题是什么、为什么需要它；
- 能否理解主要部分为何这样划分，而不只是记住名词；
- 能否知道哪些认识最重要，以及为什么；
- 不依赖子文章、卡片标题或导航链接，介绍是否仍然完整；
- 阅读具体卡片时，能否识别它讨论的是这个主题的哪一方面。

读完总览不要求立刻答出每张卡的细节，也不以记住下级目录和卡片清单作为完成标准。用户有整体认识，但在卡片中发现尚未掌握的具体问题，是正常的学习过程。

### 问题卡

问题卡是最小的复习和面试训练单元。每张卡都围绕一个问题展开，例如：

```text
HashMap 是如何解决哈希冲突的？
```

问题卡至少需要有面试问题和核心回答，才能作为一张可发布、可复习的卡片。完整解释建议作为核心内容的一部分，但具体展开程度可以不同。

以下内容按知识点需要提供，不是每张卡的必填项：

- 一句话回答：适合快速复述，面试型卡片通常应提供；
- 完整解释：说明原理、边界和取舍；
- 示例或流程：适合有操作过程或数据结构的知识；
- 常见误区：适合容易混淆的知识；
- 面试追问：适合可能继续深入的知识；
- 配套选择题：用于检查细节，不是所有卡都必须有；
- 相关问题和前置问题：通过独立的关联关系维护，不直接塞进卡片正文。

所有知识最终都可以表达为问题卡。我们不要求每个主题都必须有“基础卡、原理卡、面试卡、场景卡”等固定类型，也不要求所有卡片拥有完全相同的章节。发布审核关注的是这张卡是否能够独立帮助用户理解或回答一个明确问题。

## 知识之间如何建立联系

我们采用“**总览文章树 + 问题卡关联**”的方式。

总览文章树让用户知道主题所处的位置，总览通过概念背景和重要性判断帮助用户理解知识，页面列表让用户找到具体内容，卡片关联帮助用户辨析具体问题之间的联系。这些关系独立于总览正文维护。例如：

```text
HashMap 冲突处理问题卡
├── 前置知识：equals 与 hashCode
├── 前置知识：哈希函数和哈希冲突
├── 常见追问：HashMap 如何扩容？
├── 对比问题：HashMap 和 ConcurrentHashMap 有什么区别？
└── 应用问题：本地缓存应该如何选择 Map？
```

这些关联不是为了展示一张复杂的网络图，而是为了帮助用户继续学习：

- 不理解当前问题时，回到前置知识；
- 想继续深入时，查看追问；
- 想建立辨析能力时，查看对比问题；
- 想把知识用于工作时，查看应用问题。

用户默认看到的仍然是清晰的总览树和关联列表，而不是一张难以阅读的全量关系图。

## HashMap 的完整用户体验

一个没有背景知识的用户可以通过目录进入 `Java → 集合 → Map → HashMap`。各层级提供不同范围的介绍：

```text
集合总览：为什么需要管理一组数据，顺序、重复和查找需求为何产生不同分类
Map 总览：键值映射是什么，键的身份和相等规则为什么重要
HashMap 总览：哈希如何帮助查找，冲突为何不可避免，键稳定性和并发边界为何值得关注
```

总览正文不列出卡片清单，也不需要彼此链接。HashMap 页面另行展示具体问题，例如冲突处理、扩容和树化；用户看到列表后知道需要进一步掌握哪些细节。用户也可以直接进入该页面，总览应提供理解当前主题所需的基本背景。

打开“HashMap 如何解决哈希冲突”后，产品先展示问题，让用户自己思考。用户可以选择“显示答案”，然后依次看到：

1. 一句话回答；
2. 直观解释；
3. 具体实现；
4. 代码或流程示例；
5. 常见追问；
6. 配套选择题。

如果用户答错或表示“不会”，系统可以推荐“什么是哈希冲突”这张前置卡；如果用户已经掌握，就可以直接进入扩容、树化或并发安全等深入问题。

当用户已经熟悉 HashMap 后，他可以直接打开问题卡，跳过总览和基础解释，只进行回答、追问和复习。这也是同一套内容同时服务初学者和有经验开发者的方式。

## 复习和练习如何工作

知识学习不以“看完文章”为完成标准，而以能否回忆和表达为主要信号。

用户可以经历这样的循环：

```text
阅读总览
→ 尝试回答问题
→ 查看解释
→ 完成选择题
→ 查看追问或对比问题
→ 在复习队列中再次回答
```

选择题用于检查细节理解，问题卡用于训练主动回忆，追问和应用问题用于检查能否迁移到实际场景。用户的“会、模糊、不会”、答题结果和复习记录共同决定之后推荐什么内容。

项目已有题目复习和 FSRS 能力。知识卡可以复用复习调度的思想，但需要保留自己的学习语义：知识卡关注是否能解释和复述，LeetCode 题目关注是否能写出并通过代码。

## 和学习计划的关系

学习计划可以同时包含算法题和知识卡：

```text
本周：Java 并发
├── 学习总览：线程、锁和内存可见性
├── 问题卡：synchronized 的实现原理
├── 问题卡：volatile 能保证什么
├── LeetCode：并发或数据结构练习题
└── 复习：上周未掌握的知识卡
```

知识树和页面列表负责组织与导航，总览负责建立整体认识，卡片负责详细知识点和主动回忆，学习计划负责安排时间，复习系统负责决定什么时候再次出现。

## 首版希望用户得到的感受

首版完成后，用户应该能够：

- 通过介绍文档知道一个主题是什么、为什么包含这些内容、哪些最重要；
- 通过目录与页面列表找到子主题和具体知识点，不依赖正文内链；
- 在问题卡中先思考再查看答案；
- 通过选择题和追问检查是否真的理解；
- 从当前问题跳到前置、对比和应用知识；
- 以后直接进入问题卡进行快速复习；
- 在学习计划中同时安排知识学习和算法练习。

## 首版范围

首版先实现一条完整闭环：

1. 总览文章的主从层级，以及每个层级独立的介绍正文；
2. 页面中的子主题和问题卡列表、排序与访问入口，与正文分开维护；
3. 总览对主题范围、内容构成、概念关系和重要性的介绍，以及相应内容审核；
4. 问题卡的一句话回答、完整解释和追问；
5. 单选题或判断题；
6. 前置、追问、对比和一般关联；
7. 用户复习评级和待复习队列；
8. 学习计划中的知识卡安排；
9. 内容来源和许可证记录。

先通过 [Java 基础内容试点](java-fundamentals-pilot/README.md)验证介绍文档、独立导航和问题卡的分工，再用 Java 并发、JVM、Redis/MQ 和系统设计扩展验证练习和复习体验。更细的数据库结构、接口形式和 AI 自动生成边界在体验验证后决定。总览正文互链和逐卡导读不作为首版要求。

## 暂不提前确定的细节

以下内容等首版体验验证后再讨论：

- 是否需要独立的概念节点；
- 是否允许一张卡属于多个目录；
- 关系是否需要更多类型；
- 是否绘制可交互的关系图；
- 复习调度是否完全采用 FSRS；
- 总览文章是否支持 AI 自动生成和自动更新。
