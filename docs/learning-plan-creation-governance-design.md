# 学习计划创建治理设计

## 1. 目标

为学习计划创建链路增加三类容量保护：

- 限制单个用户可保存的正式学习计划总量；
- 限制单个用户每天可创建的学习计划草案次数；
- 分批物理删除已经过期的学习计划草案及其修订数据。

业务限制接入项目现有通用策略底座，允许管理员按全部用户、指定用户或用户组配置不同额度。清理调度参数属于节点运维参数，不进入用户策略。

## 2. 通用策略契约

策略类型：

```text
learning-plan.creation.v1
```

策略内容：

```json
{
  "maxSavedPlans": 30,
  "dailyDraftCreationLimit": 5,
  "draftRetentionDays": 14
}
```

字段语义：

| 字段 | 默认值 | 语义 |
| --- | ---: | --- |
| `maxSavedPlans` | 30 | 用户最多保留的正式计划数量；`0` 表示禁止确认新计划 |
| `dailyDraftCreationLimit` | 5 | 用户在一个配额自然日内最多成功创建的草案数量；`0` 表示禁止创建 |
| `draftRetentionDays` | 14 | 草案创建时写入的保留天数快照 |

未命中通用策略时使用代码默认值。策略读取、缓存、反序列化或校验失败时拒绝创建，不静默退回默认值。通用策略沿用全局优先级单条命中语义，因此后续可以通过高优先级指定用户策略、用户组策略覆盖全部用户策略。

管理员通过 `/admin/learning-plan-policies` 管理该类型策略，权限沿用 `policy:manage`。界面支持新建、编辑、删除、启停和完整优先级排序，并复用通用策略的全部用户、用户组和指定用户范围。清理开关、执行间隔、批大小、每日计数保留期和配额时区仍属于节点运维配置，不进入该页面。

## 3. 正式计划总量控制

确认草案时解析当前用户策略，并在同一数据库事务内：

1. 锁定该用户的学习计划创建互斥键；
2. 统计该用户当前全部正式计划；
3. 未达到 `maxSavedPlans` 时插入正式计划；
4. 更新草案确认状态。

用户级事务 advisory lock 防止两个不同草案并发确认时同时通过 `count` 检查。`ACTIVE` 和 `ARCHIVED` 都占用存储，均计入总量；用户删除计划后释放名额。

## 4. 每日草案次数控制

新增 `learning_plan_daily_draft_usage` 日计数表，以 `(user_id, quota_date)` 为主键。AI 生成草案和模板草案统一计数。

创建新草案时通过单条 PostgreSQL upsert 原子执行“未超过有效上限则加一”，并与草案插入处于同一事务。插入失败时计数一并回滚；修订已有草案不重复计数。

配额日期使用全局 `quota-zone` 计算，默认 `UTC`。用户策略可以改变每日次数，但不能改变日期边界，避免同一业务出现多套清算时区。

## 5. 草案过期与清理

草案创建时根据当次有效策略计算并固化 `expires_at`。策略后续调整不追溯修改已有草案。

清理任务按固定间隔执行，每次：

1. 使用 `FOR UPDATE SKIP LOCKED` 领取一批到期草案；
2. 删除以这些草案为目标的提案组；
3. 删除草案，利用外键级联删除草案修订；
4. 分批删除超过保留窗口的每日计数行。

多个应用节点可以同时运行清理器，`SKIP LOCKED` 保证批次不会重复领取。清理任务失败只记录低敏日志和指标，等待下一轮重试。

运维配置：

```yaml
algo-mentor:
  learning-plan:
    governance:
      quota-zone: UTC
      cleanup:
        enabled: true
        fixed-delay: 1h
        batch-size: 1000
        daily-usage-retention-days: 30
```

## 6. 错误语义

| 错误码 | HTTP 语义 | 场景 |
| --- | --- | --- |
| `LEARNING_PLAN_LIMIT_EXCEEDED` | `409 Conflict` | 正式计划已达到总量上限 |
| `LEARNING_PLAN_DRAFT_DAILY_LIMIT_EXCEEDED` | `429 Too Many Requests` | 当日草案创建次数已用尽 |
| `LEARNING_PLAN_CREATION_POLICY_UNAVAILABLE` | `503 Service Unavailable` | 通用策略无法可靠解析 |

## 7. 验证范围

- 强类型策略 JSON 字段、类型和数值边界校验；
- 未命中使用默认策略，用户/用户组命中由通用策略底座负责；
- 每日计数成功、拒绝和事务回滚；
- 不同草案并发确认不会突破正式计划上限；
- 到期草案、草案修订和目标提案组被清理，未到期草案保留；
- 清理批大小、计数数据保留期和关闭开关生效。
