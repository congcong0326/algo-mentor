# 对象相等与哈希契约总览

对象相等性规定程序在什么意义上把两个对象视为相同。它影响去重、查找和更新，也是不同类型与容器协作时需要遵守的基本约定。

例如，两次读取题目清单可能得到两个独立对象，但它们都表示标识为 `two-sum` 的题目。判断它们是否占据同一个对象身份，与判断它们是否代表同一份业务信息，是不同需求。相等性设计要先明确后一个问题的判断依据。

## 相等规则来自类型的含义

对于题目标识这样的值，只要标识内容相同，就可以定义为相等；对于具有独立生命周期的业务对象，则需要根据其身份规则决定。哪些字段参与比较，应由类型想表达的含义决定，字段数量多少并不是判断依据。

Java 提供对象身份比较，也允许类型通过 equals 定义逻辑相等。默认继承的比较行为不一定就是业务所需的规则，因此理解一种类型时，需要知道它采用哪种相等含义。

相等关系还应当能够被调用者稳定地使用。同一条件下比较结果应一致，交换比较方向不应改变结果，否则查找和去重就难以形成可靠的共同约定。具体实现需要满足的完整约束，是建立这层认识后的细节。

## 哈希帮助定位，相等规则决定匹配

如果面对大量对象，每次查找都逐个比较，工作量会随数据量增长。哈希容器利用哈希值缩小候选范围，再判断候选对象是否匹配，从而减少通常需要处理的数据。

这使相等规则与哈希规则必须相互配合：被视为相等的对象，需要产生一致的哈希值。哈希值本身仍然可能碰撞，它不能替代对逻辑相等的判断。

这里的哈希契约是类型与哈希容器之间的合作约定。并非所有容器都采用哈希方式查找，但在使用哈希容器时，两套规则的一致性直接关系到查找与去重是否正确。

## 稳定的比较依据为什么重要

对象进入容器后仍可能被其他代码持有。如果参与比较或哈希计算的状态发生变化，容器建立映射时依据的规则与后续查找时的依据就可能不再一致，原有的查找行为也就失去了可靠保证。

因此，作为键使用时，通常应当让决定键含义的数据保持稳定。不可变值类型便于满足这一点；仅固定引用变量的指向，仍不能约束可变对象内部的修改。

这个主题最重要的认识有三个：先根据类型含义定义相等，再让哈希与相等保持一致，并在使用期间保护相关状态的稳定性。哈希值如何计算、具体容器怎样处理碰撞，以及某个边界案例如何表现，都应建立在这些认识之上。
