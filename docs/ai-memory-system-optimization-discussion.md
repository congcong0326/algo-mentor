# AI 记忆系统优化方向讨论

## 文档信息

- 记录日期：2026-07-30
- 文档性质：历史方向讨论稿，部分结论已被后续决策覆盖
- 前置文档：`docs/ai-memory-system-current-state-audit.md`
- 后续设计：`docs/ai-memory-system-claim-evidence-redesign.md`
- 当前主题：让 Code Review 画像 Agent 按需探索同一道题的历史提交轨迹
- 非目标：本文不是实施计划，不在当前阶段确定数据库迁移、API 和前端最终契约

## 后续决策说明

本文件保留讨论形成过程，不作为最终实施基线。后续已经确认：

- 保留固定 5 条正式 Review 满批和非实时生效语义，不增加最大等待或用户画像实时刷新机制。
- 可溯源粒度下沉到原子 claim，不只在聚合画像条目上保存 Review ID。
- 不使用模型自报 confidence 作为写入门禁，改为服务端计算 evidence grade。
- 最终数据模型、Agent 输出、工具、API 和前端方案以 `docs/ai-memory-system-claim-evidence-redesign.md` 为准。

## 一、问题背景

当前 Code Review 画像更新使用最多 10 道不同题目的最新正式 Review，每道题只保留最新版本的轻量事实。画像 Agent 当前为单步、零工具运行，输入不包含历史代码、历史 Review 证据或完整 Review Markdown。

这种横向窗口有助于观察用户在不同题目上的当前表现，避免同一道题的多次提交过度影响画像，但无法呈现单题内部的学习过程，容易混淆以下情况：

- 用户偶尔犯错，并在下一版立即修正。
- 用户在收到建议后能够独立完成修正。
- 同一个问题在多个提交版本中持续存在。
- 同一个问题跨多道题反复出现。
- 用户曾经掌握某项能力，后续出现回退。
- 用户分数提高，但只是针对当前题目的局部修补，没有形成跨题迁移。

因此，单看最新版本难以可靠地区分“当前稳定弱点”“已经解决的问题”“持续错误模式”和“成长轨迹”。

## 二、方向结论

优化方向采用：

> 保留不同题目最新版本的横向窗口，同时允许画像 Agent 在受控范围内自主探索单题的纵向历史轨迹。

不采用以下两个极端方案：

- 不把所有题目的所有历史版本一次性塞入 Prompt，避免无效 token、延迟和噪声。
- 不允许 Agent 无边界遍历全部 Review、用户数据或原始代码，避免成本失控、选择偏差和越权风险。

横向窗口和纵向轨迹承担不同职责：

| 证据类型 | 主要用途 |
|---|---|
| 不同题目的最新版本 | 判断当前能力、跨题稳定模式和标签掌握广度 |
| 同一道题的历史版本 | 判断反馈吸收、问题修正、持续性、回退和成长速度 |

必须保持“一道题提交五版不等于完成五道题”的业务语义。同题历史只能增强轨迹证据，不能直接增加标签掌握的题目广度。

## 三、建议的第一版工具

第一版优先只增加一个核心只读工具，例如：

```text
get_problem_review_trajectory(problemSlug)
```

工具只允许读取当前 Agent invocation 用户、当前画像分析窗口内题目的历史 Review，并限制最大返回版本数。

建议返回：

- `reviewId`。
- `problemSlug`。
- `versionNo`。
- `createdAt`。
- 总分和各分项评分。
- 是否通过。
- 扣分原因。
- 改进建议。
- 受影响的受信标签。
- 相对上一版的分数变化。
- 持续存在的扣分项。
- 已解决的扣分项。
- 新出现的扣分项。

分数变化和扣分项集合差异优先由服务端确定性计算，避免让模型浪费 token 做机械比较，也降低不同模型之间的计算漂移。

## 四、原始代码读取策略

第一版不默认向画像 Agent 返回全部历史原始代码。

画像 Agent 的主要职责是分析学习轨迹，不是重新执行 Code Review。现有正式 Review 已经提供评分、扣分原因、改进建议和标签等结构化结果，应优先使用这些事实。

后续可按实际评估结果增加分层读取：

```text
结构化 Review 历史轨迹
        |
        v
仍无法判断时读取相邻版本代码 diff
        |
        v
极少数情况下读取完整历史代码
```

只有 shadow 评估证明结构化 Review 历史无法支持关键判断时，才增加代码 diff 或完整代码工具。

## 五、Agent 自主探索边界

Agent 初始输入继续包含最多 10 道不同题目的最新 Review。出现以下情况时，模型可以决定调用历史轨迹工具：

- 最新 `versionNo > 1`，且历史可能影响结论。
- 最新表现与当前画像正文存在明显矛盾。
- 需要判断某个错误是偶发、持续还是已经解决。
- 需要判断用户是否吸收了 Review 反馈。
- 准备更新 `REVIEW_AND_GROWTH_PERFORMANCE`。
- 当前证据不足以形成高置信结论。
- 最新版本出现回退，需要确认此前是否已经稳定掌握。

第一版建议设置有限的探索预算：

- Agent 最大步骤数约 4 步。
- 每个 run 最多调用 2 至 3 次历史查询工具。
- 每次只查询一个当前窗口内的 problem slug。
- 每道题最多返回最近 5 至 10 个版本。
- 工具只读，不提供任何画像写入或业务状态修改能力。

具体步数和版本数需要通过 shadow 运行的成本数据确定，不能只依赖主观估计。

## 六、画像判断规则

Agent 可以自主选择证据，但服务端和 Prompt 仍需提供确定性业务规则：

1. 同一道题的多个版本只能作为学习轨迹证据，不能作为多道题的独立掌握证据。
2. 稳定的跨题错误模式通常需要至少两道不同题目的事实支撑。
3. 已在后续版本解决的问题，不应继续表述为当前稳定弱点。
4. 如果问题反复出现，可以记录持续性，但正文应区分“同题持续”和“跨题重复”。
5. 证据不足时必须允许 `NO_CHANGE`，不能为了填充画像强行推断。
6. 代码提交历史可以支持 `REVIEW_AND_GROWTH_PERFORMANCE`，不能单独推断 `LEARNING_INTERACTION_AND_INDEPENDENCE`。
7. 标签掌握应同时关注不同题目的覆盖和最新表现，同题多版本只用于补充趋势。

## 七、输出与证据契约

历史探索不能只改善模型内部判断，还需要把判断依据带出 Agent。

建议在画像决策结构化输出中增加：

- `evidenceReviewIds`：本次结论实际使用的 Review ID。
- `confidence`：例如 `LOW / MEDIUM / HIGH`。
- `trend`：例如 `STABLE / IMPROVING / REGRESSING / INSUFFICIENT`。
- `reason`：简短说明更新或不更新的依据。

服务端应校验：

- 证据 Review 必须属于当前用户。
- 证据 Review 必须来自当前允许的分析窗口或工具返回结果。
- `REPLACE` 必须具有非空证据。
- 低置信度结果是否允许写入，需要在实施设计中明确。
- 模型不能通过输出自行扩大画像 dimension 或 tag 范围。

画像版本至少需要保存证据关联、置信度和 reason。否则新 Agent 即使判断更准确，系统仍然无法解释画像为什么变化，也无法支持后续人工核验和重新计算。

## 八、可靠性上线门槛

当前持久化队列已优化为成功确认的至少一次 callback 语义：消息先进入 `PROCESSING`，业务 callback 成功后才标记为 `SUCCEEDED`；callback、模型或工具失败时按租约和指数退避重试，达到上限转为 `FAILED` 并告警停止 topic。

多步工具 Agent 会增加以下失败点：

- 工具参数或结果校验失败。
- 数据库读取暂时失败。
- 多步模型调用超时。
- Agent 步数耗尽。
- 最终结构化输出失败。
- 画像应用时发生并发陈旧。

因此，多步历史探索不应在没有补偿能力的情况下直接上线。最低要求是提供可重试的画像更新任务，记录：

- 逻辑批次标识和幂等键。
- 输入 Review ID。
- 当前状态。
- 尝试次数。
- 最近失败类型和低敏失败原因。
- 下次重试时间。
- 最终成功时间。

可以评估修改通用队列 ack 语义，或增加画像专用的可重试 job。具体选择留待实施设计，但必须保证同一逻辑批次可以幂等重放。

## 九、验证与发布方式

第一阶段采用 shadow 模式：

- 现有 Agent 继续正常更新画像。
- 新 Agent 使用相同触发数据运行并允许查询历史。
- 新 Agent 的决策、证据、工具调用和成本只记录，不写正式画像。
- 对比旧决策和新决策后，再决定是否切换正式写入。

重点评估场景：

1. 第一版出现错误、第二版已修正，不应继续记录为当前弱点。
2. 同一错误在多个版本持续存在，应识别持续性。
3. 同一错误跨多道题出现，应识别为稳定模式。
4. 分数提高但仍依赖局部修补，不应夸大跨题掌握。
5. 用户吸收建议并独立修正，应识别成长表现。
6. 后续版本发生回退，应区分短期波动和稳定退化。

需要记录的运行指标：

- 每个 run 的工具调用次数。
- 查询的题目和历史版本数量。
- 输入、输出 token 和总成本。
- Agent 总耗时和失败率。
- `NO_CHANGE / REPLACE` 比例。
- 不同置信度和趋势的分布。
- 旧 Agent 与新 Agent 的结论差异。
- 人工抽样确认的错误画像率。

## 十、有限精力下的优先级

| 优先级 | 工作项 | 价值判断 |
|---|---|---|
| 1 | 历史轨迹工具、证据/置信度输出、可重试画像任务、shadow 评估 | 直接提升画像准确性、可解释性和可靠性，应作为同一闭环交付 |
| 2 | 为严格满 5 条增加最大等待或新的合并触发机制 | 避免低频用户长期没有系统画像 |
| 3 | 用户查看证据、纠正、抑制和删除 | 建立用户对长期记忆的控制权 |
| 暂缓 | 向量数据库、通用记忆框架、复杂语义召回 | 当前固定维度数量有限，不是主要瓶颈 |

## 十一、待讨论问题

1. 历史工具第一版只返回 Review 结构化事实，还是同步提供代码 diff。
2. 单题最多读取多少版本，是否按时间跨度额外限制。
3. Agent 是否允许自行查询当前 10 题窗口之外的题目。
4. `confidence=LOW` 时一律 `NO_CHANGE`，还是允许写入带低置信标记的画像。
5. 画像证据采用关联表，还是第一版先使用受控 JSONB。
6. 可重试能力修改通用队列，还是建立画像专用 job。
7. shadow 评估采用多少人工标注样本作为切换门槛。
