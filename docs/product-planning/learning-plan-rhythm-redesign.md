# 训练节奏重设计：从三档选择到用户自定义配置

编写日期：2026-07-07

> 本文承接 `learning-plan-living-contract-design.md`，专项解决节奏选择在执行期形同虚设的问题。

---

## 一句话结论

废弃「舒缓 / 标准 / 冲刺」三档固定选项，改为用户直接配置两个直觉参数：**每天题目数** 和 **每周训练天数**。系统以标准值为锚点给出默认值，用户随时可以调整，调整立即生效。题包实时计算，不持久化。

---

## 为什么废弃三档

三档设计存在两个根本问题：

**一、执行期形同虚设。** 节奏选完写入 metadata 之后，执行期的任何逻辑都没有读它来做差异化响应——断更容忍度、再平衡邀请、题包大小全部一样。用户选冲刺和选舒缓，体验没有任何区别。

**二、替用户做了不该做的决策。** 用户真正理解的是「我每天能投入几题」，而不是「我属于哪种节奏类型」。三档标签制造了一层不必要的抽象，且标签本身（「舒缓/标准/冲刺」）难以让用户准确判断自己属于哪档。

## 参数设计

### 两个核心参数

| 参数 | 含义 | 范围 | 默认值 | 步进 |
|------|------|------|--------|------|
| **每天题目数** | 每个题包包含的题目数量，代表用户一天的训练目标 | 1–10 题 | 按模板算（见下） | 1 题 |
| **每周训练天数** | 用户计划每周投入训练的天数 | 1–7 天 | 5 天 | 1 天 |

### 默认值的锚点逻辑

默认值以「标准节奏」为锚点，由模板的总题数和推荐周期反算：

```
每天题目数默认值 = ceil(总题数 / (推荐周数 × 5天))
```

以 NeetCode 150（推荐 12 周）为例：`ceil(150 / (12 × 5)) = 3 题/天`

这样用户拿到的默认值就是「不做任何调整，按模板节奏走」的合理起点，与原来「标准」档的语义完全对应。

### 实时估算

两个参数确定后，系统实时展示：

```
按这个配置，完成全部 150 题大约需要 10 周
```

计算方式：`ceil(剩余题数 / (每天题目数 × 每周训练天数))` 周

**展示原则：**
- 措辞用「大约」，不给精确完成日期
- 只展示「还需几周」，不展示具体日期（用户开始日期不固定、中途会调整，日期估不准不如不给）
- 参数变动时实时刷新，用户立刻感知「调大题包 → 周数变少」的联动

## 题包机制

### 定义

题包 = 计划题单中，按顺序切出的「下一批待做题目」，数量等于「每天题目数」参数。

题包不是日历概念，是顺序切片概念：
- 用户按时完成 → 每天领一包，节奏符合预期
- 用户超前 → 可以提前领取后续题包，系统给出「预计提前完成」的反馈
- 用户落后 → 未完成的题不丢失，顺延到后续题包，估算周数相应延长

### 题包实时计算，不持久化

题包在用户进入训练时按当前参数现算，不写库。已完成题目的状态持久化，题包本身不持久化。

好处：
- 参数修改立即反映，无历史数据迁移问题
- 无「旧题包还没做完但参数已变」的状态不一致
- 服务端维护压力极小

### 顺序不变原则

无论参数如何调整，题单顺序始终不变。调整参数只改变「每次切多少题」，不影响题目的排列顺序。

## 创建流程

从模板创建时，用户在原有模板选择之后，配置节奏参数：

```
选择模板  →  配置节奏  →  生成草案
```

节奏配置区域展示：

```
每天题目数    [ − ]  3  [ + ]
每周训练天数  [ − ]  5  [ + ]

按这个配置，完成全部 150 题大约需要 12 周
```

用户可以在此调整，也可以直接用默认值生成草案。

## 执行期调整

### 入口

计划详情页新增「调整节奏」按钮，用户主动点击进入弹窗。

### 弹窗内容

```
调整训练节奏

每天题目数    [ − ]  3  [ + ]
每周训练天数  [ − ]  5  [ + ]

当前：每天 3 题 · 每周 5 天 · 还需约 10 周
调整后：每天 5 题 · 每周 6 天 · 还需约 5 周

        [ 取消 ]  [ 确认调整 ]
```

用户在弹窗内看到新旧对比，确认前知道会发生什么变化。

### 生效时机

确认后**立即生效**：

- 下一个题包按新参数切出
- 已完成题目不受影响
- 题单顺序不变，顺序连续，无割裂感

**为什么立即生效而不是「等下一包」：** 题包是顺序切片，调整只改切片大小，已完成的部分天然不受影响，不存在状态冲突，因此立即生效是正确且简单的选择。

---

## 超前完成的反馈

用户提前领取后续题包时，系统给出正向反馈：

```
本包完成 · 数组与哈希（3/3）
路线进度  27 → 30 题
还需约 9 周 → 还需约 8 周  ↑ 提前约 1 周

下一包已就绪：二分与区间（3 题）
              [ 继续下一包 ]  [ 今天到这 ]
```

超前带来的奖励是可见的「预计缩短时间」，激励用户保持高投入。

---

## 再平衡邀请（断更回归）

用户断更后回归，系统不再展示「要不要切档」，而是直接展示参数调整建议：

```
欢迎回来 · 你有 4 天没训练
未完成的 6 题已顺延，还需约 11 周（原来约 10 周）

现在的节奏对你有点紧，要不要调整一下？
  每天题目数从 3 题 → 2 题，还需约 14 周

        [ 保持不变 ]  [ 调整为每天 2 题 ]
```

更具体，用户更容易做决定，不需要理解「舒缓/冲刺」的抽象含义。

## 数据模型变化

### 需要持久化

| 数据 | 说明 |
|------|------|
| 每天题目数 | 用户当前配置，随调整更新 |
| 每周训练天数 | 用户当前配置，随调整更新 |
| 已完成/跳过的题目状态 | 原有，不变 |

### 不持久化（实时计算）

| 数据 | 说明 |
|------|------|
| 当前题包内容 | 按顺序和参数现算 |
| 剩余题数 | 总题数 - 已完成 - 已跳过 |
| 还需约几周 | 实时估算 |

### 可以清理的历史字段

原 `metadata` 中的 `RHYTHM_MODE`（`RELAXED/RECOMMENDED/SPRINT`）不再需要，可随迭代逐步清理。后端 `LearningPlanRhythmMode` 枚举和 `rhythmOptions` 相关计算逻辑可整体移除。

---

## 与「活的契约」的关系

本设计与活的契约的三条承诺完全兼容，且表达更简洁：

| 承诺 | 如何体现 |
|------|---------|
| **不丢题** | 未完成题顺延，顺序不变 |
| **不设墙** | 随时可以提前领取后续题包 |
| **有回声** | 调整参数 → 「还需几周」实时变化；完成题包 → 周数实时缩短 |

---

## 本版不做的事（边界）

- 不做精确完成日期预测，只给「大约几周」
- 不做每日推送通知，所有提示在用户主动进入时触发
- 不做题单内容的自动调整，只改每包切片大小
- 不绑定具体面试日期（deadline 型是独立扩展点）
