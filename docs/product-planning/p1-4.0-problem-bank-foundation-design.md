# P1-4.0 题库基座：官方 API 全量构建与校验设计

## 背景

`algo-mentor` 的所有高阶能力——公司维度元数据（P1-4.0-A）、冲刺模式题单、按目标公司出题的模拟面试、知识点标签与能力画像——都建立在同一个底层题库 `problem` 之上。题库的**覆盖度和正确性**是这些能力的可信上限。

当前题库现状：

- 由 `tools/problem_seed/prepare_seed.py` 从本地 `fishjar/leetcode-problemset` 生成 `data/seed/problems.jsonl`。
- 2026-07-02 核对：共 **1828 题**，来源 commit `6bd9323f1a542eac6997f9f76656842333d96c45`，快照较旧。
- 每题字段：`slug`、`frontendId`、EN/ZH 题面、`difficulty`、tags、`codeSnippets`（Python3 模板）、`sampleTestCase`。
- 后端 `ProblemSeedImporter` 按行 upsert 进 `problem` 表（迁移 `V11__rebuild_problem_i18n_schema.sql`：`slug`/`frontend_id` 唯一、tag 三数组等长约束）。

**设计方向**：既然中英文题面都能从 LeetCode 官方直接获取，题库改为**以官方 API 为唯一内容源、全量构建**，不再依赖 `fishjar` 等第三方快照仓库。第三方仓库（`azl397985856`、`afatcoder/LeetcodeTop`）最多降级为**可选交叉校验**，不进入题库内容。

**推进策略：分三阶段，先抓取、再画像、再加工。** 不预先拍板「要不要 AI 翻译」「要不要收录只有中文的题」这类策略，而是先把原始数据抓到本地，用真实分布（多少题符合要求、多少只有中文没英文、多少中文缺失）驱动后续加工决策。

> 关键事实：`fishjar` 的 JSON 字段（`questionFrontendId`/`titleSlug`/`content`/`translatedContent`/`topicTags`/`codeSnippets`/`sampleTestCase`）本就是官方 GraphQL 的原样字段——fishjar 当年就是抓官方的。因此 `prepare_seed.py` 现有的解析逻辑（`html_to_markdown`/`read_tags`/`read_difficulty`/`normalize_slug` 等纯函数）几乎可直接复用，只把输入从「本地仓库目录」换成「抓取的官方 JSON」，迁移风险很低。

本设计对应产品演进大纲中 **4.0 知识聚合层 / 内容中台** 的事实底座部分，是 P1-4.0-A 公司元数据的前置。

## 目标

- 以官方 API 全量构建题库：英文题面来自 `leetcode.com`，中文题面来自 `leetcode.cn`，按 `slug` join。
- **分阶段推进**：阶段一原始抓取入本地 → 阶段二数据画像分类 → 阶段三数据驱动加工入库。
- 保证抓取 → 归一 → 入库的**字段映射正确、结构约束通过**（核心诉求）。
- 完整性可度量（免费题覆盖率），加工策略基于真实数据分布而非预设。
- 整个链路**可重复、可增量、可审计**：pin 抓取快照、画像/校验报告。

## 非目标

- 不获取或存储 LeetCode Premium **受锁题面**：Premium 题只保留题号/slug/难度/外链。
- 不导入 `azl397985856` 等第三方仓库的**题解正文**（版权较重的原创题解，非题面）。
- 不做真实判题、代码运行或自建测试集。
- 第一版不做定时抓取 worker；先离线脚本抓取 + 现有后端导入链路入库。5.3 内容运营期再升级为 worker + 差异对比 + 灰度。

> 注意：「是否 AI 翻译补齐中文缺失题」「是否收录只有中文的 CN-only 题」**不列为非目标**，而是阶段三的数据驱动决策（见「阶段三」）——先看阶段二画像的真实数字再定。

## 内容源：LeetCode 官方 API

「官方 API」实为两个官方端点，按 `slug` join，二者都是官方，仍满足「不依赖第三方仓库」：

| 端点 | 提供 |
|---|---|
| `leetcode.com` 全量清单 `api/problems/all/` | 全球站题目列表：`frontendId`、`titleSlug`、`difficulty(level)`、`paid_only`、总题数 |
| `leetcode.cn` 全量清单 | 中文站题目列表（含 CN-only 题：剑指 Offer / LCP / LCR / 面试题） |
| `leetcode.com` GraphQL 单题 | 英文题面 `content`、结构字段 `topicTags`/`codeSnippets`/`sampleTestCase`/`difficulty`/`isPaidOnly`/`questionFrontendId` |
| `leetcode.cn` GraphQL 单题 | 中文题面 `translatedTitle`、`translatedContent`、中文 `topicTags[].translatedName` |

- 抓取阶段把 `.com` 与 `.cn` 两个清单**合并成 union 索引**，每题标注 `onCom` / `onCn` / `paidOnly`，从而能区分「两站都有」「只有 .com」「只有 .cn（CN-only）」。
- Premium（`paid_only = true`）题无法合规获取正文，只保留题号/slug/难度/外链，进入画像的 `premium_locked` 类。

### 第三方仓库定位（降级为可选）

| 源 | 新定位 | 说明 |
|---|---|---|
| `fishjar/leetcode-problemset` | **退役** | 由官方 API 全量构建取代 |
| `azl397985856/leetcode` | 可选交叉校验 | 只读文件名 `{号}.{slug}.md` 抽 `号↔slug`，抽查 slug 改名；题解正文不入库 |
| `afatcoder/LeetcodeTop` | 可选交叉校验 + 公司频率 | 用链接抽 slug 抽查；公司频率见 P1-4.0-A |

第三方交叉校验对本设计**非必需**：官方 API 即真值，校验主要靠自洽性（见「阶段二 · 校验规则」）。

## 阶段一 · 原始抓取入本地（raw ingest，不做取舍）

目标：把官方原始数据**尽量完整**地落到本地，不在这一步做转换或丢弃，让后续分析基于真实数据。

- 抓 `.com` + `.cn` 全量清单 → `data/index/problem_index.jsonl`（union 索引，含 `onCom`/`onCn`/`paidOnly`）+ 快照 manifest（pin 抓取日期、两站总题数）。
- 对每题抓**可得的原始 JSON**：`.com` 英文单题、`.cn` 中文单题，各自缓存到本地，不转换。仅真正锁死无正文可取的 Premium 记为 locked。
- CN-only 题也一并抓 `.cn` 原始 JSON（这一步不判断是否收录）。
- 稳健性：限速（约 1–2 req/s）、失败指数退避重试、断点续抓（已抓 slug 跳过）、合理 UA。
- 产物：
  - `data/index/problem_index.jsonl`
  - `data/sources/leetcode-api/{slug}.com.json`、`{slug}.cn.json`

## 阶段二 · 数据画像与分类（profiling，只读分析）

目标：用真实数据回答「符合要求的有多少、只有中文没英文的有多少、中文缺失的有多少」，产出决策依据。

对本地缓存逐题分类：

| 类别 | 判定 | 含义 |
|---|---|---|
| `complete` | EN 正文 + ZH 正文都齐 | 符合要求，可直接归一入库 |
| `zh_missing` | 有 EN 无 ZH（新题/冷门题 `.cn` 无翻译） | **中文缺失** |
| `cn_only` | 只有 ZH 无 EN（`.cn` 独有，或 `.com` 锁而 `.cn` 有） | **只有中文没有英文** |
| `premium_locked` | 两端都拿不到正文 | 只能留外链 |
| `deprecated` | 清单有但抓取 404 | 已下架/改名 |

产出 `data/reports/profile_report.json`：各类计数、难度分布、标签分布、每类若干示例 slug。

同时做**校验规则**（正确性 + 一致性，只读，不阻断抓取）：

- 正确性：`difficulty ∈ {EASY,MEDIUM,HARD}`；`slug`/`frontendId` 唯一；`leetcode_url` 与 slug 一致；tag 三数组可等长（对齐 `ck_problem_tag_array_lengths`）。
- 一致性：`.com` 与 `.cn` 对同一 slug 的 `frontendId` 必须一致，不一致进报告（`.cn` 改题/滞后信号）。
- 完整性：`免费题覆盖率 = complete 的免费题 / .com 免费题总数`，输出百分比与缺口数。

## 阶段三 · 加工处理与策略决策（processing，数据驱动）

目标：基于阶段二画像，逐类决定处理方式，产出最终 seed 并入库。**AI 翻译、CN-only 收录等都是这一阶段的可选项，取决于阶段二的数字。**

| 类别 | 处理决策（待阶段二数据后定） |
|---|---|
| `complete` | 直接按「字段映射」归一入库 |
| `zh_missing` | 二选一：① 先英文回退展示（`title_zh`/`content_zh` 回退 EN，标记 `zh_missing`）；② 上 AI 翻译补中文（评估成本/质量后决定，单独设计） |
| `cn_only` | 是否收录（面向国内用户价值高）；收录则英文侧如何处理（保留中文 + 英文留空或机翻） |
| `premium_locked` | 只保留 slug/难度/外链白名单 |
| `deprecated` | 进报告人工确认，不直接删除 |

加工后归一为 `problems.jsonl` → `validate_seed.py` 校验 → 现有 `ProblemSeedImporter` 幂等 upsert 入库。

### 字段映射（官方 API → `problem` 表）

`complete` / 收录类归一到入库列的固定口径：

| `problem` 列 | 来源字段 | 归一处理 |
|---|---|---|
| `slug` | `.com titleSlug`（CN-only 用 `.cn titleSlug`） | `normalize_slug` |
| `frontend_id` | `questionFrontendId` | 转 int |
| `title_en` | `.com title` | trim；CN-only 缺失按阶段三决策处理 |
| `title_zh` | `.cn translatedTitle` | 缺失回退 `title_en` |
| `difficulty` | `difficulty` | 映射 `EASY`/`MEDIUM`/`HARD` |
| `tag_values` | `.com topicTags[].slug` | 去重排序 |
| `tag_labels_en` | `.com topicTags[].name` | 与 `tag_values` 对齐 |
| `tag_labels_zh` | `.cn topicTags[].translatedName` | 缺失回退英文标签，保持三数组等长 |
| `content_markdown_en` | `.com content`（HTML） | `html_to_markdown` |
| `content_markdown_zh` | `.cn translatedContent`（HTML） | `html_to_markdown`，缺失回退 EN |
| `leetcode_url` | 由 slug 拼 | `https://leetcode.com/problems/{slug}/`（CN-only 用 `.cn`） |
| `sample_test_case` | `sampleTestCase` / `exampleTestcases` | 原样 |
| `python3_template` | `codeSnippets[langSlug=python3].code` | 原样 |
| `source_commit` | —— | 官方无 git commit，改写为**抓取快照标识**（如 `leetcode-api@2026-07-02`）；`VARCHAR(80)` 列可复用，语义需清晰时后续迁移改名 `source_snapshot` |

`title_zh`/`content_markdown_zh` 有 `NOT NULL` 约束，`tag` 三数组必须等长；任一缺失都按上表回退，不破坏约束。

## 数据模型影响

- 第一版**不改** `problem` schema。`source_commit` 列复用为「抓取快照标识」；若需语义清晰可后续迁移改名 `source_snapshot`。
- 可选（建议阶段三后）：新增 `problem_import_run` 审计表，与 P1-4.0-A 的 `problem_company_import_run` 风格一致，记录 `source_snapshot`、`index_snapshot_at`、`complete`/`zh_missing`/`cn_only`/`premium_locked`/`error` 计数、`report_json JSONB`。

## 合规与稳健性

- 官方 GraphQL：合理 UA、限速（约 1–2 req/s）、失败指数退避重试、只抓可得正文。
- pin 抓取日期与两站总题数到 manifest，保证结果可复现、可审计。
- 全量首抓约 3000+ 题 × 2 端点，需分批，预估时长写入 manifest。
- 抓取产物默认本地/内部，不提交仓库；产品展示以 LeetCode 外链为权威入口，**不对外分发受版权保护的题面**（对齐产品演进大纲「4.0 合规红线」）。
- 若官方接口不可持续或触发频控：以已抓部分为准，缺口只在报告标注。

## 与初版方案的差异（明确记录）

| 维度 | 初版 | 本版 |
|---|---|---|
| 内容源 | fishjar 本地快照为基线 | 官方 API（.com EN + .cn ZH）为唯一内容源 |
| 推进方式 | 一次性回填缺题 | 分三阶段：抓取 → 画像 → 加工 |
| 加工策略 | 预设（不做翻译、不收 CN-only） | 数据驱动（阶段二画像后再定 AI 翻译 / CN-only） |
| fishjar | 现有内容基线 | 退役 |
| azl / LeetcodeTop | 校验清单（必需） | 可选交叉校验（非必需） |

## 测试计划

- 阶段一 `fetch_*`：mock GraphQL/清单响应，验证 union 索引、限速、断点续抓、只抓可得正文。
- 阶段二 `profile_problems.py`：`complete`/`zh_missing`/`cn_only`/`premium_locked`/`deprecated` 五类判定正确；`.com/.cn` frontendId 一致性校验。
- 阶段二 `validate_seed.py`：每条正确性规则命中与放行（缺字段、错枚举、tag 数组不等长、slug 重复、slug 与 URL 不一致）。
- 阶段三 `prepare_seed.py`：官方 `.com`+`.cn` JSON 样例 → `SeedProblem`（在现有 `prepare_seed_test.py` 基础上扩展 join + 回退）。
- 导入幂等：以现有 `ProblemSeedImporterTest` 为基线，验证 seed 重复导入幂等。

## 上线顺序

1. **阶段一（先抓取入本地）**：`fetch_problem_index` + `fetch_problem_details`，把 `.com`+`.cn` 原始数据落到本地缓存，断点续抓直到全量。
2. **阶段二（画像分类）**：`profile_problems` + `validate_seed`，产出 `profile_report.json`——拿到「complete / zh_missing / cn_only / premium / deprecated」的真实数字。
3. **决策点**：基于画像与你确认 AI 翻译、CN-only 收录、覆盖率阈值等策略（见「待确认」）。
4. **阶段三（加工入库）**：按决策 `prepare_seed` → `validate_seed` → 小批打通（~100 题人工核对 EN/ZH）→ 全量归一入库，幂等覆盖旧的 1828。
5. **验收**：复核免费题覆盖率与抽样正确性。
6.（可选）增量抓取 + `problem_import_run` 审计表。
7. 题库稳定后再叠 P1-4.0-A 公司信号。

## 风险与约束

- **官方抓取 ToS/频控**：限速、仅本地、外链为权威；不可持续则以已抓部分为准。
- **`.cn` 无翻译**：进 `zh_missing` 类，阶段三决定回退或机翻。
- **`.com`/`.cn` slug 差异与 CN-only 题**：union 索引标注来源，阶段三决定是否收录。
- **Premium 扩大**：只能保留外链，覆盖率分母只算免费题。
- **官方字段/接口变更**：解析层加容错、校验层兜底，字段缺失进报告而非静默入库。

## 待确认（多数在阶段二画像后再定）

- `zh_missing` 类：先英文回退展示，还是上 AI 翻译补齐（单独评估成本/质量）。
- `cn_only` 类：是否收录剑指 Offer / LCP / LCR / 面试题等；收录则英文侧如何处理。
- 免费题覆盖率验收阈值（建议 95%，Premium 不计入分母）。
- `source_commit` 列是否迁移改名为 `source_snapshot`。
- 抓取节奏与是否需要代理/镜像；单次全量抓取的时间预算。
