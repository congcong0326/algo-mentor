# 训练方案负载计算与周执行闭环设计

编写日期：2026-07-07

## 一句话结论

训练方案的「周期 / 每周投入」不应该只是表单字段，而应该统一进入一套负载模型：生成前判断是否可执行，生成时约束题量和复盘量，生成后按周桶追踪进度。模板入口用「推荐 / 舒缓 / 冲刺」降低配置负担，AI 个性化入口保留「周期 + 每周投入」，但两者底层共用同一套容量、负载和周进度闭环。

## 背景问题

当前学习计划已经有两种创建入口：

- AI 个性化生成：用户选择周期、每周投入、目标、水平、语言、难度和主题。
- 从模板创建：用户选择模板后，也可以修改周期和每周投入。

现状的主要问题不是字段缺失，而是字段后果不明显：

- 模板草稿会接收 `durationWeeks` 和 `weeklyHours`，但主要只是把周期均分到阶段、把每周投入写进摘要；题目数量和执行强度基本不变。
- AI 生成 prompt 会接收 `weeklyHours`，但现有硬约束主要是阶段数和每阶段最多 5 题，没有把每周投入转成总题量、难度组合或复盘预算。
- 计划保存后，详情页能看到题目状态，但用户不知道自己相对当前周是正常、落后还是超前。

这会造成产品上的断裂：用户以为自己配置了时间预算，但系统没有明确告诉他「这份计划按你的时间是否可执行」以及「这周该完成什么」。

## 目标

- 让用户在创建计划时知道计划强度是否合理。
- 让模板入口的时间配置从自由输入升级为可理解的节奏选择。
- 让 AI 入口的周期和每周投入成为实际生成约束，而不是 prompt 装饰。
- 让正式计划进入统一的周执行闭环：本周目标、已完成、落后/超前、下一步建议。
- 第一版避免复杂实时调度，不做每天排程，不因每道题状态变化重排整份计划。

## 非目标

- 不做真实在线判题，正确性仍以 LeetCode 通过和现有 Review 闭环为主。
- 不做精确到分钟的学习时长预测。
- 不做实时自动重排计划；第一版只做页面加载或进度变更时的重新计算。
- 不强制用户按系统日期完成任务；周进度是反馈和建议，不是惩罚机制。

## 核心设计原则

### 两个入口，一套底层

模板入口和 AI 入口的前端表达可以不同，但底层必须统一：

```text
训练容量 = 周期 × 每周投入 × 容量系数
题目负载 = 难度权重 + 专题修正 + 复盘缓冲
计划强度 = 题目负载 / 训练容量
```

任何计划都必须回答三件事：

- 这份计划总负载大概是多少？
- 用户给出的时间容量是否足够？
- 如果不够，系统如何调整或提示？

### 模板是策展路线，不是自由生成

从模板创建时，模板的价值是稳定、可审计、被整理过的路线。因此用户不应该像 AI 创建一样自由改所有参数。更合理的表达是：

- 推荐：采用模板默认周期和投入，完整路线。
- 舒缓：拉长周期，保留完整路线，增加复盘缓冲。
- 冲刺：压缩周期或提高每周投入，必要时只保留核心题，减少 optional 或加练内容。

### AI 是预算约束下的定制生成

AI 个性化入口仍然保留周期和每周投入，因为它的产品语义是「我有多少时间，想达成什么目标」。但生成结果必须落在预算内：

- 时间不足时，生成轻量核心计划，而不是硬塞完整路线。
- 时间充裕时，增加复盘、二刷和同主题强化，而不是简单增加题量。
- 生成后由后端负载校验，不符合预算时要求修订或给出明确警告。

### 执行闭环先按周，不按天

第一版只需要把计划落到每周桶：

```text
第 1 周：目标 12 题，预计 8h
已完成 5/12，落后 3 题
下一步：继续完成数组与哈希剩余题
```

这比每日排程简单，也更符合刷题训练的不确定性。

## 负载模型

### 估算单位

引入 `loadPoint` 作为内部估算单位。第一版不追求精确，只要足够稳定、可解释、可调参。

建议初始权重：

| 项 | 负载点 |
| --- | ---: |
| Easy | 1 |
| Medium | 2 |
| Hard | 3 |
| 图论 / 动态规划 / Hard 专题修正 | +0.5 |
| 首轮 Review / 错题复盘缓冲 | 每题 +0.5 |

建议初始容量：

```text
每周容量 = weeklyHours × 1.0 loadPoint
总容量 = durationWeeks × weeklyCapacity
```

这里的 `1.0` 是第一版校准参数，后续可通过真实完成数据调整。

### 强度分级

```text
loadRatio = totalLoad / totalCapacity
```

| loadRatio | 分级 | 产品含义 |
| ---: | --- | --- |
| <= 0.85 | 舒缓 | 有复盘和缓冲空间 |
| 0.85 - 1.10 | 合理 | 推荐执行强度 |
| 1.10 - 1.30 | 偏紧 | 需要稳定投入，适合冲刺 |
| > 1.30 | 过载 | 不建议完整执行，需要延长周期、增加投入或减少题量 |

所有展示都应使用「估算」「大约」「建议」等措辞，避免制造虚假的精确感。

## 模板创建体验

### 入口形态

模板卡片继续展示默认节奏：

```text
默认 4 周 · 8h/周
69 道本地可练题
推荐强度：偏紧
```

选中模板后，不再展示自由数字输入，改成节奏选项：

| 模式 | 行为 | 适合用户 |
| --- | --- | --- |
| 推荐 | 使用模板默认周期和每周投入，保留完整本地匹配题 | 大多数用户 |
| 舒缓 | 周期拉长或每周题量降低，保留完整路线，增加复盘缓冲 | 时间更分散、希望稳步学 |
| 冲刺 | 周期压缩或每周投入提高；容量不足时保留核心题 | 有明确 deadline 的面试用户 |

### 模式映射建议

第一版可以使用确定性规则：

- 推荐：`defaultDurationWeeks` + `defaultWeeklyHours` + `FULL_ROUTE`。
- 舒缓：`ceil(defaultDurationWeeks × 1.5)`，每周投入可沿用默认或降低 20%，`FULL_ROUTE_WITH_REVIEW_BUFFER`。
- 冲刺：优先提高每周投入到默认的 125% 到 150%；如果仍过载，进入 `CORE_ONLY`。

其中 `CORE_ONLY` 的题目选择第一版可以按以下优先级：

1. 过滤 `metadata.optional = true` 的题。
2. 过滤本地缺失题和 premium-only 题。
3. 按模板原始顺序保留核心题。
4. 若仍过载，优先保留 Easy/Medium 中覆盖不同 pattern 的题，Hard 作为加练。

后续模板 seed 可以补充 `priority` 或 `core` 字段，让核心题选择更稳定。

### 创建前反馈

用户选择节奏后，立即展示负载摘要：

```text
预计 6 周完成 69 题
每周约 11-12 题
预计负载 82 点 / 容量 96 点
强度：合理
包含每周复盘缓冲
```

如果过载：

```text
当前节奏偏紧：预计负载 82 点 / 容量 48 点。
建议改为舒缓模式，或使用冲刺核心题版本。
```

### 生成结果

模板草稿仍保持确定性，不调用 AI：

- 阶段来自模板阶段。
- 题目来自模板本地匹配 refs。
- 根据节奏模式生成周桶。
- 草稿 metadata 中记录 `templateId`、`rhythmMode`、`coveragePolicy`、`loadSummary`、`weeklyBuckets`。

## AI 创建体验

### 表单保留周期和每周投入

AI 入口继续保留：

- 周期。
- 每周投入。
- 训练场景。
- 当前水平。
- 难度分布。
- 主题偏好。

但提交后要新增「预算解释」：

```text
你给出的预算是 4 周 × 3h/周，适合 12-16 道核心题 + 每周复盘。
如果想覆盖 Blind 75 级别路线，建议提高到 4 周 × 10h/周，或延长到 8 周。
```

### 生成约束

AI prompt 和后端 validator 需要共同约束：

- 输出计划总负载应落在容量范围内。
- 每阶段题目数不只受「每阶段最多 5 题」限制，还要受总容量限制。
- 周期短、投入少时，优先生成核心题和复盘任务。
- 周期长、投入多时，增加复盘、加练和阶段验收，不盲目堆题。

建议在 prompt 中新增结构化约束：

```text
totalCapacityPoints: 24
targetLoadRange: 18-26
weeklyCapacityPoints: 6
loadPolicy: FIT_USER_BUDGET
```

生成后由 `LearningPlanDraftValidator` 或新的负载校验服务做二次校验。若明显过载：

- 第一版：返回草稿，但标记 `loadRisk = OVERLOADED` 并展示建议。
- 后续版：自动触发一次修订，要求模型减少题量或降低难度。

## 周执行闭环

### 周桶定义

一个周桶包含：

- `weekIndex`
- `title`
- `plannedProblemCount`
- `plannedLoadPoints`
- `problemSlugs`
- `reviewAdvice`
- `status`

第一版可以不新增数据库表，先根据计划快照中的阶段和题目顺序在读取详情时计算。若后续要支持用户手动调整周计划，再持久化 `plannedWeek` 和 `estimatedLoadPoints`。

### 当前周计算

```text
currentWeek = floor((today - plan.startDate) / 7) + 1
```

第一版可以用计划创建时间作为 `startDate`；如果产品要支持「下周一开始」，再给计划增加显式 `startDate`。

### 进度计算

利用现有题目进度状态：

- `COMPLETED` 计入完成负载。
- `SKIPPED` 不计完成，但在统计中单独展示。
- `IN_PROGRESS` 可以计入题数进度，但不计入完成负载。
- `NOT_STARTED` 不计。

核心指标：

```text
expectedLoadToDate = 当前周及以前应完成的负载
completedLoad = 已完成题目的负载
loadGap = completedLoad - expectedLoadToDate
```

状态建议：

| 状态 | 条件 |
| --- | --- |
| 超前 | `completedLoad >= expectedLoadToDate + 1 周容量 × 0.5` |
| 正常 | `completedLoad` 接近 `expectedLoadToDate` |
| 有风险 | 落后小于 1 周容量 |
| 落后 | 落后超过 1 周容量 |

### 详情页展示

计划详情页新增周节奏区域：

```text
当前第 2 周 / 共 6 周
本周目标：11 题，预计 8 点负载
本周已完成：5 题
整体节奏：有风险，落后约 4 点负载
下一步：继续完成「二分、区间与树」阶段剩余题
```

题目列表仍按阶段展示，但可以补充周标签：

```text
第 2 周 · 二分搜索
```

### 建议卡片

第一版只做轻量建议，不自动修改计划：

- 落后：建议本周优先完成核心题，暂缓 optional。
- 明显落后：建议延长周期或切换为核心题版本。
- 超前：建议追加 2-3 道同主题强化题。
- 某类 Review 不达标多：建议下周减少新题，增加复盘。

建议卡片先只作为提示；后续再支持一键采纳并生成计划扩展或调整。

## 技术方案

### 后端新增应用服务

建议放在 `mentor-application` 的 learning plan 边界内：

- `LearningPlanLoadEstimator`：根据题目难度、标签和复盘策略估算负载。
- `LearningPlanCapacityCalculator`：根据周期和每周投入计算容量。
- `LearningPlanWeeklyBucketPlanner`：按阶段、题目顺序和容量生成周桶。
- `LearningPlanPaceService`：结合当前日期和题目进度计算节奏状态。
- `LearningPlanLoadPolicy`：描述 `FULL_ROUTE`、`CORE_ONLY`、`REVIEW_HEAVY` 等策略。

### 后端改动点

- 模板草稿生成：`LearningPlanTemplateDraftService` 使用节奏模式和负载策略，而不是直接使用自由 `durationWeeks` / `weeklyHours`。
- AI 草稿生成：`LearningPlanDraftPromptBuilder` 注入容量和目标负载范围。
- 草稿校验：在 `LearningPlanDraftValidator` 中增加负载校验或委托给新服务。
- 计划详情 API：返回 `loadSummary`、`weeklyBuckets`、`paceSummary`。
- 模板 API：返回每个模板的推荐强度和可用节奏模式。

### 前端改动点

- `LearningPlanTemplateCreatePanel`：自由数字输入改为节奏 segmented control。
- `LearningPlanCreateForm`：AI 创建保留周期和每周投入，但提交前/提交后展示预算解释。
- `PlanPreview`：展示负载摘要和每周题量。
- `LearningPlanDetail`：展示当前周、进度偏差和建议卡片。
- `frontend/src/types/api.ts`：补充 `loadSummary`、`weeklyBuckets`、`paceSummary` 类型。

### 数据持久化策略

MVP 建议先不新增表：

- 草稿和正式计划中的周桶可以从计划快照计算。
- 题目进度继续复用现有 practice progress 状态。
- `loadSummary` 可以作为 draft/plan metadata 写入，便于审计和回放。

当需要支持用户手动拖动周计划、冻结某周安排或长期统计预测时，再新增结构化表。

## 分阶段落地

### 阶段一：负载估算和创建闭环

目标：让时间配置立刻有可见后果。

- 新增负载估算服务和单元测试。
- 模板入口改为「推荐 / 舒缓 / 冲刺」。
- 模板草稿 metadata 写入 `rhythmMode`、`coveragePolicy`、`loadSummary`。
- AI prompt 注入容量和目标负载范围。
- 预览页展示总负载、容量、强度和每周大致题量。

验收：

- 同一个模板选择不同节奏，预览中的周期、每周题量和强度明显不同。
- AI 选择低投入时，不再生成明显过载计划，或至少展示过载风险。

### 阶段二：周桶和详情页进度

目标：让正式计划知道「本周该做什么」。

- 生成或计算 weekly buckets。
- 计划详情返回 `paceSummary`。
- 前端展示当前周、本周目标、已完成和落后/超前状态。
- 题目完成后刷新详情，周进度随之变化。

验收：

- 用户能在计划详情页看到本周目标和当前节奏。
- 完成题目后，周进度和整体节奏正确更新。

### 阶段三：建议卡片和轻量调整

目标：从进度展示升级到下一步行动建议。

- 落后、超前、Review 不达标等场景生成建议卡片。
- 建议先只展示，不自动改计划。
- 后续接入已有计划扩展能力，支持一键追加、压缩或延长。

验收：

- 落后用户能得到明确下一步建议。
- 建议卡片点击率和采纳率可观测。

## 指标

建议新增业务埋点或后端统计：

- 模板节奏选择分布：推荐 / 舒缓 / 冲刺。
- 创建时强度分布：舒缓 / 合理 / 偏紧 / 过载。
- 过载提示出现率和用户调整率。
- AI 计划的负载校验失败率或过载风险率。
- 周节奏状态分布：超前 / 正常 / 有风险 / 落后。
- 建议卡片曝光、点击和采纳率。
- 计划确认后 7 天内完成至少 1 周目标的比例。

## 风险与应对

### 估算不准

负载模型一定不精确。第一版要把它定位为「节奏估算」，避免承诺每题真实耗时。后续用实际完成数据校准权重。

### 冲刺模式削掉关键题

如果没有稳定的 core 标记，冲刺模式可能误删重要题。第一版要保守：优先删 optional 和 Hard 加练，不随意删覆盖关键 pattern 的核心题。后续在模板 seed 中补 `priority` 或 `core`。

### 周进度制造压力

进度反馈应偏教练式，而不是打卡惩罚。文案上使用「建议」「有风险」「可以调整」，避免制造失败感。

### 实现范围膨胀

第一版不要做每日排程、实时重排和复杂预测。只做创建校验、周桶、详情页进度和轻量建议。

## 评审待定问题

1. 计划是否需要显式 `startDate`，还是第一版先用创建时间？
2. 冲刺模式是否允许自动进入 `CORE_ONLY`，还是必须让用户二次确认？
3. 模板 seed 是否在下一批就补 `priority/core` 字段？
4. AI 过载时第一版是直接返回带风险提示的草稿，还是自动触发一次修订？
5. weekly buckets 第一版是否只计算返回，还是写入 plan metadata 便于回放？

## 推荐决策

建议第一版采用最小可闭环方案：

- 模板入口立即改为「推荐 / 舒缓 / 冲刺」。
- AI 入口保留周期和每周投入，但接入容量约束和负载校验。
- 周执行闭环先按周桶计算，不新增复杂排程表。
- 计划详情先展示进度偏差和建议，不自动重排。

这样可以在不引入过高业务复杂度的前提下，让两个创建方向都形成清晰闭环。
