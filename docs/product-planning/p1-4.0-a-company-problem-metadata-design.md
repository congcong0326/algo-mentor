# P1-4.0-A 公司维度题目元数据设计

## 背景

`algo-mentor` 的长期付费人群里，社招跳槽和临近面试的求职用户更关心「现在该刷哪些高频题」，其中国内求职者还关心「目标公司的目标岗位（前端/后端/算法/客户端）考哪些题」。现有题库已经能按关键词、难度、标签和分类查题，但缺少「目标公司 + 岗位 + 频率」的事实信号，导致冲刺模式、模拟面试和计划推荐只能按通用标签排序。

本设计对应产品演进大纲中的 **P1-4.0-A 公司维度题目元数据**，在 **P1-4.0 题库基座**（见 `p1-4.0-problem-bank-foundation-design.md`）补齐并校验后的 `problem` 题库上，叠加事实元数据。第一版不新增题面、不做判题、不复制题解。

本次相较初版的主要变化：**加入国内公司源 `afatcoder/LeetcodeTop`，并引入「岗位（role）」维度**，让公司信号从「欧美公司为主 + 仅时间窗口」扩展到「国内大厂 + 分岗位」。

## 目标

- 导入公开的「公司 × 岗位 × 题目 × 频率 / 时间桶」元数据，作为选题、排序和题单生成信号。
- 覆盖国内主流大厂（阿里、腾讯、字节、美团、快手、百度等）与欧美公司两类来源。
- 支持题库页、Agent 查题工具和后续冲刺模式按目标公司 + 岗位筛题。
- 在所有产品展示中带来源说明，保持 LeetCode 题面和判题的权威入口。
- 保持导入链路可审计：记录来源仓库、commit、匹配数、未匹配数和错误数。

## 非目标

- 不导入或分发 LeetCode 题面、Premium 内容正文、他人题解原文、测试用例或代码答案。
- 不新增真实判题、代码运行或自建测试集。
- 第一版不做定时 worker；先用脚本生成 seed，再由后端导入。
- 第一版不把未知题目写入产品查询结果，只进入导入报告。

## 数据源策略

第一版采用「多源归一 + 统一 seed 格式 + 后端导入」。所有源都归一到同一套 `problem_company_signal` 事实模型，靠 `source_name` 区分来源，靠 `role` / `recency_bucket` 承载不同源的维度。

### 欧美主源（时间桶维度）

- 仓库：[`liquidslr/leetcode-company-wise-problems`](https://github.com/liquidslr/leetcode-company-wise-problems)
- 用途：欧美公司主信号源，数据较新，按公司目录组织。
- 维度：**时间桶**（30 天 / 3 月 / 6 月 / 更早 / 全部），**无岗位维度**（role 记为 `GENERAL`）。
- 2026-07-02 核对结果：
  - GitHub API 返回 `license: null`，仓库无明确开源许可证。
  - 默认分支为 `main`。
  - 公司目录下桶文件格式为 `1. Thirty Days.csv`、`2. Three Months.csv`、`3. Six Months.csv`、`4. More Than Six Months.csv`、`5. All.csv`。
  - CSV header 示例为 `Difficulty,Title,Frequency,Acceptance Rate,Link,Topics`。

### 国内主源（岗位维度）

- 仓库：[`afatcoder/LeetcodeTop`](https://github.com/afatcoder/LeetcodeTop)
- 用途：国内大厂主信号源，补齐 `liquidslr` 缺失的国内公司与岗位维度。
- 2026-07-02 核对结果：
  - GitHub API 返回 `license: null`，无开源许可证；README 要求「引用频率数据或转载需**注明本仓库地址**」。
  - 覆盖公司：`alibaba`、`amazon`、`baidu`、`bytedance`、`kuaishou`、`meituan`、`microsoft`、`shopee`、`tencent`、`yuanfudao`（猿辅导）。
  - 目录结构为 `公司/岗位.md`，岗位文件如 `backend.md`、`frontend.md`、`algorithm.md`、`client.md`、`test.md`、`data.md`；部分公司只有单一 `SDE`/汇总文件。
  - 文件内为 Markdown 表格，列为 `题目 | 出现次数 | 链接`，例如：
    - `1. 两数之和 | 4 | https://leetcode-cn.com/problems/two-sum`
    - `415. 字符串相加 | 14 | https://leetcode-cn.com/problems/add-strings`
  - 维度：**岗位**（role），**无时间桶**（recency_bucket 统一记为 `ALL_TIME`）。
  - 频率：`出现次数` 作为 `frequency_score`（整数），链接域名为 `leetcode-cn.com`，个别行链接指向微信文章等非题目页。

### 兜底源

- 仓库：[`hxu296/leetcode-company-wise-problems-2022`](https://github.com/hxu296/leetcode-company-wise-problems-2022)
- 许可证：MIT License。
- 用途：补缺和回归测试样本，不作为新鲜度主信号。

### 合规处理

两个主源都无 LICENSE，第一版统一按「事实公开 + 来源注明 + 不分发原文内容」处理：

- 可以在产品中展示公司、岗位、频率、时间桶、题目外链和来源。
- 不复制题面、题解、测试用例或任何长文本内容。
- `LeetcodeTop` 额外满足其「注明本仓库地址」要求：产品展示与 API 返回都带 `sourceName` / `sourceUrl` 指向该仓库。
- 由主源生成的 seed 默认用于本地/内部导入；若要提交到仓库，需要再做许可复核。
- 产品页和 API 返回都保留 `sourceName`、`sourceUrl`，详情页说明「公司频率数据来自公开元数据源，题面以 LeetCode 为准」。

## 总体方案

第一版采用「离线准备 + 后端导入」的轻量链路：

1. `tools/problem_company_seed/prepare_company_seed.py` 拉取或读取外部源（CSV / Markdown）。
2. 脚本按源类型解析：`liquidslr` 走公司目录 + 时间桶 CSV；`LeetcodeTop` 走公司目录 + 岗位 Markdown 表格。归一化题目 slug、公司 slug、岗位、频率、排名和来源信息。
3. 脚本生成本地 seed：
   - `problem_company_signals.jsonl`
   - `problem_company_seed_manifest.json`
4. 后端导入 seed，按 `problem.slug` 匹配现有题库。
5. 匹配成功的信号写入 `company` 和 `problem_company_signal`。
6. 未匹配 slug、非题目链接、重复行、解析错误写入 manifest 和 `problem_company_import_run` 报告。

> 依赖：`LeetcodeTop` 大量国内高频题依赖题库已覆盖对应 slug；题库覆盖度由 **P1-4.0 题库基座**保证。题库先补齐能显著降低本环节 unmatched 率。

后续 5.3 内容运营期再升级为独立 worker，支持定时拉取、人工审核、差异对比和灰度发布。

## 归一化规则

### 题目匹配

- 从表格 `Link` 提取 LeetCode URL 中的 `/problems/{slug}`，**兼容 `leetcode.com` 与 `leetcode-cn.com` 两种域名**。
- 优先用 `slug` 匹配现有 `problem.slug`。
- `LeetcodeTop` 标题为中文数字题名（如 `1. 两数之和`），**只靠链接取 slug，不用标题猜题**。
- 如果 URL 缺失、指向非题目页（如微信文章）或无法解析，不入库，只记入错误/未匹配报告。
- 未匹配题目不进入 `problem_company_signal`，避免前端展示无法打开的本地题目。

### 公司 slug

- 公司目录名转为稳定 `company.slug`：trim → 转小写 → 非字母数字连续替换为 `-` → 去掉首尾 `-`。
- `display_name` 保留目录原名的可读形式；国内公司可经别名表补中文名（如 `tencent` → `腾讯`），别名表缺失时回退英文目录名。
- 若未来出现同 slug 不同显示名，以最近一次导入的目录名更新 `display_name`，但保留同一个 `company.id`。

### 岗位 role

`LeetcodeTop` 的岗位文件名映射到内部枚举；无岗位维度的源（`liquidslr` / `hxu296`）统一记为 `GENERAL`。

| 原始文件名 | 内部枚举 |
|---|---|
| `backend` / 后端 | `BACKEND` |
| `frontend` / 前端 | `FRONTEND` |
| `algorithm` / 算法 | `ALGORITHM` |
| `client` / 客户端 | `CLIENT` |
| `test` / 测试 | `TEST` |
| `data` / 数据 | `DATA` |
| `SDE` / 汇总 / 无岗位源 | `GENERAL` |

未知岗位文件名进入错误报告，不静默归入 `GENERAL`。

### 时间桶

`liquidslr` 有时间桶；`LeetcodeTop` 无时间桶，统一记为 `ALL_TIME`。

| 原始文件名 | 内部枚举 |
|---|---|
| `Thirty Days` | `THIRTY_DAYS` |
| `Three Months` | `THREE_MONTHS` |
| `Six Months` | `SIX_MONTHS` |
| `More Than Six Months` | `MORE_THAN_SIX_MONTHS` |
| `All` / 无桶源 | `ALL_TIME` |

### 频率与排名

- 保留原始频率为 `frequency_score`（`liquidslr` 的 `Frequency` 小数、`LeetcodeTop` 的 `出现次数` 整数），使用 decimal，**不做跨源重标定**。
- 同一 `(company, role, recency_bucket, source_name)` 内按 `frequency_score DESC` 生成 `rank`。
- 默认排序：`rank ASC` → `frequency_score DESC` → `problem.frontend_id ASC NULLS LAST`。
- 若同一源同一导入批次出现重复 `(company_slug, role, problem_slug, recency_bucket)`：
  - 保留 `frequency_score` 更高的一行。
  - 分数相同则保留排名更靠前或先出现的一行。
  - manifest 记录去重数量。

### 字段限制

- `Title` / 中文题名仅用于导入诊断和人工核对，不进入产品 API 主查询结果。
- `Topics` 可进入 manifest 供后续标签补全评估，第一版不自动写回 `problem.tag_values`。
- `Acceptance Rate`（仅 `liquidslr` 有）作为外部源事实字段保存为 `acceptance_rate`，但前端第一版可以不展示。

## 数据模型

### `company`

记录公司维度实体，供过滤项、题单和导入统计复用。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGSERIAL PRIMARY KEY` | 公司内部 ID |
| `slug` | `VARCHAR(160) UNIQUE NOT NULL` | 稳定筛选值，例如 `tencent` |
| `display_name` | `VARCHAR(200) NOT NULL` | 展示名，例如 `腾讯` |
| `problem_count` | `INTEGER NOT NULL DEFAULT 0` | 最近一次导入后覆盖的去重本地题目数 |
| `source_count` | `INTEGER NOT NULL DEFAULT 0` | 最近一次导入后覆盖的来源信号数 |
| `last_imported_at` | `TIMESTAMPTZ` | 最近导入时间 |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | 更新时间 |

索引：

- `uk_company_slug(slug)`
- `idx_company_last_imported_at(last_imported_at DESC)`

### `problem_company_signal`

记录题目在公司、岗位和时间桶下的频率事实。**相较初版新增 `role` 维度并纳入唯一键。**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGSERIAL PRIMARY KEY` | 信号 ID |
| `problem_id` | `BIGINT NOT NULL REFERENCES problem(id) ON DELETE CASCADE` | 本地题目 |
| `company_id` | `BIGINT NOT NULL REFERENCES company(id) ON DELETE CASCADE` | 公司 |
| `role` | `VARCHAR(40) NOT NULL DEFAULT 'GENERAL'` | 岗位枚举，无岗位源为 `GENERAL` |
| `recency_bucket` | `VARCHAR(40) NOT NULL` | 内部时间桶枚举，无桶源为 `ALL_TIME` |
| `frequency_score` | `NUMERIC(8, 3)` | 外部源频率分 / 出现次数 |
| `rank` | `INTEGER` | 公司 + 岗位 + 时间桶内排名 |
| `acceptance_rate` | `NUMERIC(10, 8)` | 外部源通过率字段 |
| `source_name` | `VARCHAR(120) NOT NULL` | 来源名 |
| `source_url` | `TEXT NOT NULL` | 来源仓库或文件 URL |
| `source_commit` | `VARCHAR(80)` | 导入时 pin 的 commit |
| `source_problem_url` | `TEXT` | LeetCode 题目外链 |
| `import_run_id` | `BIGINT REFERENCES problem_company_import_run(id)` | 导入批次 |
| `created_at` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | 更新时间 |

约束与索引：

- 唯一键：`(problem_id, company_id, role, recency_bucket, source_name)`
- 查询索引：`(company_id, role, recency_bucket, rank)`
- 题目详情索引：`(problem_id, company_id, role, recency_bucket)`
- 来源追踪索引：`(source_name, source_commit)`

### `problem_company_import_run`

记录每次导入的审计信息。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `BIGSERIAL PRIMARY KEY` | 导入批次 ID |
| `source_name` | `VARCHAR(120) NOT NULL` | 来源名 |
| `source_repo_url` | `TEXT NOT NULL` | 来源仓库 |
| `source_commit` | `VARCHAR(80)` | 导入时 commit |
| `seed_manifest_path` | `TEXT` | 本地 manifest 路径或对象存储 key |
| `started_at` | `TIMESTAMPTZ NOT NULL` | 开始时间 |
| `finished_at` | `TIMESTAMPTZ` | 结束时间 |
| `status` | `VARCHAR(30) NOT NULL` | `SUCCESS` / `PARTIAL_SUCCESS` / `FAILED` |
| `company_count` | `INTEGER NOT NULL DEFAULT 0` | 公司数量 |
| `source_signal_count` | `INTEGER NOT NULL DEFAULT 0` | 源数据有效行数 |
| `matched_signal_count` | `INTEGER NOT NULL DEFAULT 0` | 入库信号数 |
| `unmatched_problem_count` | `INTEGER NOT NULL DEFAULT 0` | 未匹配题目数 |
| `duplicate_signal_count` | `INTEGER NOT NULL DEFAULT 0` | 去重数量 |
| `error_count` | `INTEGER NOT NULL DEFAULT 0` | 错误数量（非题目链接、未知岗位等） |
| `metadata_json` | `JSONB NOT NULL DEFAULT '{}'::JSONB` | 未匹配摘要、错误摘要、桶/岗位统计 |

## Seed 文件格式

### `problem_company_signals.jsonl`

每行一个归一化信号（新增 `role`）：

```json
{"companySlug":"tencent","companyName":"腾讯","role":"FRONTEND","problemSlug":"add-strings","recencyBucket":"ALL_TIME","frequencyScore":14.0,"rank":1,"acceptanceRate":null,"sourceName":"afatcoder/LeetcodeTop","sourceUrl":"https://github.com/afatcoder/LeetcodeTop","sourceCommit":"<commit_sha>","sourceProblemUrl":"https://leetcode-cn.com/problems/add-strings"}
```

欧美源示例（`role` 为 `GENERAL`）：

```json
{"companySlug":"amazon","companyName":"Amazon","role":"GENERAL","problemSlug":"two-sum","recencyBucket":"THIRTY_DAYS","frequencyScore":100.0,"rank":1,"acceptanceRate":0.00576889423655172,"sourceName":"liquidslr/leetcode-company-wise-problems","sourceUrl":"https://github.com/liquidslr/leetcode-company-wise-problems","sourceCommit":"<commit_sha>","sourceProblemUrl":"https://leetcode.com/problems/two-sum"}
```

### `problem_company_seed_manifest.json`

记录导入前诊断：

```json
{
  "sourceName": "afatcoder/LeetcodeTop",
  "sourceRepoUrl": "https://github.com/afatcoder/LeetcodeTop",
  "sourceCommit": "<commit_sha>",
  "generatedAt": "2026-07-02T00:00:00Z",
  "companies": 0,
  "roles": 0,
  "signals": 0,
  "duplicates": 0,
  "errors": [],
  "unmatchedProblems": []
}
```

`unmatchedProblems` 由后端导入阶段补充，因为只有后端能基于当前数据库判断 slug 是否存在。

## 后端导入设计

第一版建议放在 `backend/mentor-api` 题库边界内复用现有 `problem` 表和 MyBatis 设施，不新增独立 worker 模块。

建议新增：

- `api.problem.company.model`：`Company`、`ProblemCompanySignal`、`ProblemCompanyRole`、`ProblemCompanyRecencyBucket`、`ProblemCompanyImportRun`
- `api.problem.company.service`：`ProblemCompanySeedImportService`、`ProblemCompanySeedReader`
- `api.problem.company.repository`：`ProblemCompanyRepository`、`MyBatisProblemCompanyRepository`
- `mapper/problem/ProblemCompanyMapper.xml`

导入语义：

- 每次导入创建一条 `problem_company_import_run`。
- 对 `company.slug` 做 upsert。
- 对匹配成功的信号做 upsert（唯一键含 `role`），重复导入同一 seed 保持幂等。
- 导入完成后重新计算每个 company 的 `problem_count`、`source_count`、`last_imported_at`。
- 如果源文件无 LICENSE，不读取或保存题面字段；导入服务只接受 seed 中的事实字段。

## API 设计

现阶段兼容扩展已有 `/api/admin/problems`，后续冲刺模式上线时再补产品化 `/api/problems` 或题单 API。

### 查询参数

扩展 `GET /api/admin/problems`：

| 参数 | 说明 |
|---|---|
| `company` | 公司 slug，例如 `tencent` |
| `role` | 岗位枚举，例如 `FRONTEND`，默认 `GENERAL` |
| `recencyBucket` | 时间桶，默认 `ALL_TIME` |
| `sort=company_frequency_desc` | 按公司高频信号排序 |

约束：

- 当 `sort=company_frequency_desc` 时必须提供 `company`。
- `role` 和 `recencyBucket` 仅在 `company` 存在时生效。
- 未匹配公司返回空列表，而不是回退到全题库，避免误导。

### 返回类型

扩展 `ProblemListItem`（signal 增加 `role`）：

```ts
export type ProblemCompanyRole =
  | 'GENERAL' | 'BACKEND' | 'FRONTEND' | 'ALGORITHM' | 'CLIENT' | 'TEST' | 'DATA';

export interface ProblemCompanySignal {
  companySlug: string;
  companyName: string;
  role: ProblemCompanyRole;
  recencyBucket: 'THIRTY_DAYS' | 'THREE_MONTHS' | 'SIX_MONTHS' | 'MORE_THAN_SIX_MONTHS' | 'ALL_TIME';
  frequencyScore?: number;
  rank?: number;
  sourceName: string;
  sourceUrl: string;
}

export interface ProblemListItem {
  slug: string;
  frontendId?: number;
  title: string;
  difficulty?: ProblemDifficulty;
  tags: ProblemTag[];
  companySignals?: ProblemCompanySignal[];
}
```

列表页默认只返回当前筛选公司、岗位和时间桶对应的 signal，避免每行展开所有公司信号。

### 过滤项

扩展 `ProblemFilters`：

```ts
export interface ProblemCompanyFilterOption {
  slug: string;
  name: string;
  problemCount: number;
  roles: ProblemCompanyRole[];
  lastImportedAt?: string;
}
```

`ProblemFilters.companies` 返回可筛选公司、覆盖题目数、**该公司可用岗位**和最近导入时间。默认按 `problemCount DESC, name ASC` 排序。岗位下拉根据所选公司的 `roles` 动态填充。

## Agent 工具扩展

现有工具边界保持不变：`list_problem_filters` 发现过滤空间，`search_problems` 返回轻量题目列表，`get_problem_statement` 按 slug 读取题面。

扩展 `list_problem_filters`：

- 返回 `companies`，每个公司带 `roles`。
- 返回 `sorts` 增加 `company_frequency_desc`。
- `notes` 增加说明：公司筛选必须使用 `companies[].slug`，岗位必须使用该公司 `roles` 中的值。

扩展 `search_problems` 输入：`company`、`role`、`recencyBucket`、`sort=company_frequency_desc`。

扩展 `search_problems` 输出列表项：`companySignals`（含 `role`）。

工具边界：

- `search_problems` 仍不返回题面正文、题解正文、代码模板或 seed 原始文件内容。
- 如果公司参数不存在，工具返回明确错误并提示先调用 `list_problem_filters`。
- 如果 `role` 不在该公司可用岗位内，工具返回参数错误。
- 如果 `sort=company_frequency_desc` 但未传 `company`，工具返回参数错误。

## 前端展示策略

题库页：

- 在现有关键词、难度、标签筛选旁增加公司筛选。
- 选择公司后显示：
  - 岗位 segmented control（`不限` / `后端` / `前端` / `算法` / `客户端` / `测试` / `数据`，仅显示该公司可用岗位）。

## 风险与约束

- 两个主源均无 LICENSE：不得提交原始文件或题面/题解派生内容，展示必须带来源；`LeetcodeTop` 额外注明仓库地址。
- LeetCode slug 可能变更：导入时以当前本地 `problem.slug` 为准，未匹配需要进入报告；国内高频题的匹配率依赖 **P1-4.0 题库基座**的覆盖度。
- 频率分不可跨源比较：`liquidslr` 的 Frequency 与 `LeetcodeTop` 的出现次数量纲不同，只在同一公司、岗位、时间桶、来源内排序，不合并计算。
- 时间桶语义来自外部源文件名，不等价于实时统计窗口；`LeetcodeTop` 无时间桶，UI 文案应避免承诺「近 N 天」。
- 岗位维度只在 `LeetcodeTop` 存在；欧美源统一 `GENERAL`，前端不应对欧美公司展示岗位筛选。
- 公司名可能包含并购、别名或大小写差异，后续需要运营别名表（含中文显示名）。

## 待确认

- 由无 LICENSE 主源生成的 `problem_company_signals.jsonl` 是否允许进入私有仓库；默认建议不提交，仅本地生成并导入。
- 是否需要后台管理页展示 import run 详情；第一版可以先用日志和数据库查询。
- 是否在详情页展示 `acceptanceRate`；第一版建议不展示，避免用户误读为本地通过率。
- 公司中文显示名别名表由谁维护、放代码常量还是配置/数据表。
