# 知识库维护约定

本目录是共享知识库的正式内容源。首次维护时读取 [README.md](README.md) 的相关规则；同一会话已读取且未变化的规范无需重复读取。

- 仅 `.node` 目录、`.card.md` 和 `.article.md` 文件进入知识库；其他目录整个子树不扫描。
- 一张卡片一个文件，文件名是问题，YAML front matter 的 slug 是长期身份。修改或移动保留 slug，新问题使用新 slug。
- 元数据后到第一个顶层二级标题之前是核心回答，之后全部是详细 Markdown，不限定章节。
- 卡片关系只能通过 slug 引用。日常制卡不主动运行校验工具；校验统一交给导入环节（`make knowledge-import` 已包含校验），用户明确要求时可单独执行 `make knowledge-validate`。
- 用户要求修改内容时可直接编辑；执行导入按当前会话授权范围进行，不自动发布到外部环境。
- 大纲标题默认不加编号；范围和 GitHub 固定版本来源集中写在主题级 README。新建或修改卡片以主题 README 的版本和范围为准；历史调研记录不作为制卡必读材料，仅在调整主题范围、追溯来源或解决资料冲突时按需查阅。事实核验只读取当前问题相关的权威资料。
- 新建或调整大纲先维护主题目录的 `outline.json`，再执行 `make knowledge-outline-preview KNOWLEDGE_OUTLINE=清单路径`；确认与本次任务一致后用 `knowledge-outline-apply` 补建目录。已有会话授权足够时直接继续，不为例行生成再次询问。
- 标题不可包含 `/`、`\` 等路径分隔符；工具遇到非法名称会拒绝生成。空叶子使用 `.gitkeep`，不要批量生成相同 README。
- 改名、移动应先预览，再显式迁移目录并保留卡片 slug；生成器不会自动删除、移动或覆盖内容。`make knowledge-validate` 和 `make knowledge-import` 均会先核对清单与完整路径。
- 工具自动复用已核验的构建；只有需要强制更新外部依赖或构建环境时执行 `make knowledge-cli-rebuild`，不要手动跳过检查。

## 卡片写作风格

卡片用于面试准备和知识复习。读者应能快速找到答案，用自己的话复述，并在展开详情后理解关键原因。新建和修改卡片统一采用“直接回答、围绕主线解释、按需补充边界”的风格，深度与主题约定的读者水平一致。统一的是表达原则，不要求每张卡使用相同的章节、篇幅或材料组合。

### 内容取舍

- 一张卡围绕标题中的问题展开。写作前先确定直接结论，以及理解结论必需的几个要点；正文围绕这些要点组织。
- 技术深度体现在把关键原因和过程讲清楚。只补充能解释主结论、影响实际选择或纠正常见误解的细节，不因知识相关就全部展开。
- 会改变主结论成立条件的边界就近说明；常见但次要的误区放到详情。罕见例外、实现优化和相邻专题，除非标题涉及或省略会造成误导，否则不主动扩展。
- 已有其他卡片承载的内容，只保留理解本题所需的说明，必要时通过 slug 建立关系，避免重复展开。

### 核心回答

- 第一两句直接回答标题，随后说明最关键的原因、区别或选择依据。标题有多个子问时，应覆盖各子问，形成可独立复述的完整回答。
- 使用自然的面试口述表达，通常用一至三段短段落，读完可以在约半分钟到一分钟内讲清主结论；这是控制信息量的参考，不是必须凑满的时长或硬性字数限制。
- 每句话集中表达一个意思。解释必要术语，避免连续堆叠限定语、抽象名词或长串并列项；并列信息确实更易比较时可以用简短列表。
- 核心回答应独立成立，但不承担所有追问。源码字段、详细步骤、长例子和次要边界留给详情，不在开头堆满提醒与例外。

### 详细解释

- 按读者理解问题的顺序展开，先讲主要机制或规则，再用必要的例子说明结果，最后补充影响使用的边界。章节标题直接指出要解释的问题，不强制套用固定模板。
- 比较类问题围绕一致的维度说明差别，机制类问题讲清关键过程，选择类问题连接条件与选择理由。一个问题兼有多种性质时，围绕其主要目的组织，不必逐套展开。
- 涉及机制时，把“结构或规则 → 操作过程 → 行为或成本”的因果关系讲通，选择足以解释结论的层次即可。需要时深入数据结构、执行过程或源码，不为体现深度而罗列字段、版本差异和复杂度。
- 示例应短而集中，每个示例验证一个明确结论，并用文字说明原因。优先使用直观的数据和场景，不为一个简单结论搭建无关的业务模型或完整程序。
- 表格用于对比，代码用于展示行为，Mermaid 用于解释难以用文字讲清的关系或流程；按需选择，不要求每张卡都具备。每一节都应推进解释，避免重复核心回答或在结尾再次总结相同结论。
- 保持技术准确，区分语言或 API 契约与特定版本的实现细节。必要的限定要写清楚，但不在每段附加泛泛的免责声明，也不使用缺乏条件的绝对结论或性能排名。

### 交付前自查

- 只读核心回答，能否直接回答标题，并自然地复述？
- 展开详情，是否真正解释了关键原因或过程，而不是换句话重复结论？
- 每一节是否服务于本题？删掉某个细节若不影响理解、选择或关键边界，就考虑删减或交给相关卡片。
- 是否有连续堆叠的术语、长句、重复提醒，或为追求完整而加入的旁支？在保留准确性与关键解释的前提下精简。

以上为内容自查，不要求额外运行校验工具。
