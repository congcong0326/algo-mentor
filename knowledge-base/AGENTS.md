# 知识库维护约定

本目录是共享知识库的正式内容源。首次维护时读取 [README.md](README.md) 的相关规则；同一会话已读取且未变化的规范无需重复读取。

- 仅 `.node` 目录、`.card.md` 和 `.article.md` 文件进入知识库；其他目录整个子树不扫描。
- 一张卡片一个文件，文件名是问题，YAML front matter 的 slug 是长期身份。修改或移动保留 slug，新问题使用新 slug。
- 元数据后到第一个顶层二级标题之前是核心回答，之后全部是详细 Markdown，不限定章节。
- 卡片关系只能通过 slug 引用。日常制卡不主动运行校验工具；校验统一交给导入环节（`make knowledge-import` 已包含校验），用户明确要求时可单独执行 `make knowledge-validate`。
- 用户要求修改内容时可直接编辑；执行导入按当前会话授权范围进行，不自动发布到外部环境。
- 大纲标题默认不加编号；范围和 GitHub 固定版本来源集中写在主题级 README。新建或修改卡片以主题 README 的版本和范围为准；历史调研记录不作为制卡必读材料，仅在调整主题范围、追溯来源或解决资料冲突时按需查阅。熟悉且稳定的知识不为制卡机械检索；框架实例作为论据时，在卡片参考中给出对应的官方文档或固定版本源码。遇到版本差异、实现细节或不确定事实时，只核验当前问题相关的权威资料。
- 新建或调整大纲先维护主题目录的 `outline.json`，再执行 `make knowledge-outline-preview KNOWLEDGE_OUTLINE=清单路径`；确认与本次任务一致后用 `knowledge-outline-apply` 补建目录。已有会话授权足够时直接继续，不为例行生成再次询问。
- 标题不可包含 `/`、`\` 等路径分隔符；工具遇到非法名称会拒绝生成。空叶子使用 `.gitkeep`，不要批量生成相同 README。
- 改名、移动应先预览，再显式迁移目录并保留卡片 slug；生成器不会自动删除、移动或覆盖内容。`make knowledge-validate` 和 `make knowledge-import` 均会先核对清单与完整路径。
- 工具自动复用已核验的构建；只有需要强制更新外部依赖或构建环境时执行 `make knowledge-cli-rebuild`，不要手动跳过检查。

## 卡片写作风格（非常重要）

卡片用于面试准备和知识复习，应体现资深工程师的理解与判断，让读者既能复述答案，也能理解背后的原理。围绕问题自由组织内容，章节、篇幅、示例和图表按表达需要决定，无需套用固定模板或逐项凑齐材料。

- **直接回答**：核心回答简洁、自然地回答标题，能够独立理解和复述；深入分析放在详情。
- **有深度**：讲透关键原理、实现过程和设计取舍，按需深入源码。鼓励融入有价值的工程经验，让读者理解行为为何发生、条件变化后会怎样，以及实践中如何判断和选择。
- **有广度**：优先联系 Spring、Jackson、MyBatis、Netty、Tomcat 等常见开源框架的真实应用，解释框架如何运用本题的机制。有助于理解时可以跨框架比较，关联应自然、具体。
- **表达清楚**：围绕主线讲解，保留有解释价值的细节，删去重复和无关旁支。深度来自分析，广度来自联系，避免堆砌术语、源码或框架名称。
- **准确可信**：说清影响结论的重要条件，区分通用规则与特定版本实现；不虚构源码、引用、数据或亲历经验，简化伪代码应标明。
- **按需查证**：默认使用已有的可靠知识，熟悉且稳定的内容直接写。仅对影响结论的不确定事实、拿不准的版本或源码细节，以及用户明确要求核验的内容，针对性查阅权威资料。
