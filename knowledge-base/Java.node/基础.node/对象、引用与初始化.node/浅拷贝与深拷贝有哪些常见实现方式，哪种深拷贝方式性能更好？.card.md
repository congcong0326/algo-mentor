浅拷贝可以用复制构造器、`clone()`、数组和集合的复制方法实现；Spring 的 `BeanUtils.copyProperties()` 也只复制属性值，内部可变对象仍可能共享。深拷贝需要继续复制约定范围内的可变对象：可以显式逐层复制，也可以把可序列化的对象图写入字节流再读出。Spring Framework 6.2.19 的 `SerializationUtils.clone()` 就封装了后一种 JDK 序列化做法。

**对象结构明确且关注性能时，通常优先显式复制。** 它只创建需要隔离的对象；JDK 序列化和 Spring 的封装还要遍历对象图、生成字节数据并重新解析。`clone()` 加手动补拷与复制构造器没有固定的速度排名，最终要在复制结果相同的前提下按实际数据测量。

## 常见浅拷贝方法停在哪一层

| 方法 | 实际复制的内容 |
| --- | --- |
| 复制构造器或工厂方法直接赋值字段 | 创建新外层对象，引用字段仍指向原内部对象 |
| `super.clone()` | 按字段复制对象；引用字段仍保存原引用，类需实现 `Cloneable` |
| 引用数组的 `clone()`、`Arrays.copyOf()`，或 `new ArrayList<>(oldList)` | 创建新数组或列表，元素对象仍共享 |
| Spring `BeanUtils.copyProperties(source, target)` | 把可复制属性的值写入已有目标对象，不会递归复制属性指向的对象 |

深拷贝可以从这些浅拷贝结果出发，再替换需要隔离的引用字段；也可以直接在复制构造器或工厂方法中逐层创建副本。不可变值可以共享，关键是会被修改的状态是否仍由原件和副本共同持有。

## 显式深拷贝怎样写

下面的 `Hint` 可变；`Problem` 的显式复制新建 `Hint`，但共享不可变的 `String`：

```java
final class Hint implements java.io.Serializable {
    String text;
    Hint(String text) { this.text = text; }
}

final class Problem implements java.io.Serializable {
    String title;
    Hint hint;
    Problem(String title, Hint hint) {
        this.title = title;
        this.hint = hint;
    }

    Problem deepCopy() {
        return new Problem(title, hint == null ? null : new Hint(hint.text));
    }
}
```

这里实现 `Serializable` 是为了让下文的序列化方案也能复制这组对象；显式复制本身不需要它。如果 `Problem` 后来增加可变字段，`deepCopy()` 也要重新检查。若对象图含循环或多个字段指向同一个对象，显式复制还需记录“原对象 → 副本”的身份映射，避免无限递归并保留原有的共享关系。

## JDK 序列化为什么能复制对象图

用 `ObjectOutputStream.writeObject()` 把对象写入内存字节流，再由新的 `ObjectInputStream.readObject()` 读出，就能得到按序列化规则重建的对象图：

```java
import java.io.*;

static <T extends Serializable> T copyBySerialization(T source)
        throws IOException, ClassNotFoundException {
    ByteArrayOutputStream bytes = new ByteArrayOutputStream();
    try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
        out.writeObject(source);
    }
    try (ObjectInputStream in = new ObjectInputStream(
            new ByteArrayInputStream(bytes.toByteArray()))) {
        @SuppressWarnings("unchecked")
        T copy = (T) in.readObject();
        return copy;
    }
}
```

`writeObject()` 会沿可序列化字段遍历引用。流用句柄记录已写过的对象，所以同一内部对象被多处引用时，读出的图仍保持这种共享关系，也能处理循环引用。根对象及其需要写入的内部对象都必须支持序列化，否则可能抛出 `NotSerializableException`；默认序列化不会保存 `transient` 和 `static` 字段。自定义序列化或 `readResolve()` 还可能改变重建结果，因此“反序列化得到新对象”不等于所有业务状态都被完整、独立地复制。

## Spring 的 deep clone 与 JDK 做法有什么关系

Spring Framework 6.2.19 的 `org.springframework.util.SerializationUtils.clone(original)` 要求参数类型实现 `Serializable`。它内部调用 `serialize()` 再调用 `deserialize()`，底层仍是 `ObjectOutputStream`、`ObjectInputStream` 和内存字节数组。因此它继承 JDK 序列化的图结构处理能力、字段规则和运行成本；它不是比 JDK 序列化更快的另一种深拷贝算法。

```java
Problem original = new Problem("两数之和", new Hint("先枚举"));
Problem copy = org.springframework.util.SerializationUtils.clone(original);
System.out.println(copy.hint == original.hint); // false
```

`BeanUtils.copyProperties()` 处理的是 JavaBean 属性值复制，不能代替 `SerializationUtils.clone()`。例如某个可读写的 `hint` 属性保存了 `Hint` 引用，复制后目标属性仍会指向原 `Hint`，除非调用者随后显式复制并替换它。

## 怎样判断哪种方式性能更好

显式复制通常省去字节流、类型元数据处理和中间字节数组，适合结构稳定且需要频繁复制的对象。`clone()` 加补拷也可以只创建必要对象，但与复制构造器谁更快取决于实现和 JVM 优化。JDK 序列化适合已有 `Serializable` 对象图、需要自动保留共享关系与循环、且能接受序列化开销的场景；Spring `SerializationUtils.clone()` 主要节省调用代码，不消除序列化成本。

比较性能时要让各实现复制同样的可变状态、保留同样的共享关系，再测量吞吐、延迟和分配量。仅比较“生成了一个新外层对象”的耗时，会把浅拷贝误判为更快的深拷贝。
