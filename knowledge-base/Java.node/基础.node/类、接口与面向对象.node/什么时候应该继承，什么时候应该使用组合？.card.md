**需要把新类型当作已有类型使用，并且能遵守已有类型的全部对外契约时，才考虑继承；只是要使用另一个对象的能力时，使用组合。** 继承建立子类型关系，调用方可以把子类对象交给接受父类型的代码。组合则把协作者作为成员持有，通过委托完成工作，不会自动让外层对象成为协作者的子类型。

“能复用父类代码”不足以决定继承：子类还会继承可访问的 API，并受父类构造过程、可重写方法及扩展约定影响。若只想替换一个算法或复用部分行为，优先考虑组合；需要统一调用契约时，可让不同实现共同实现一个接口。

## 判断类型关系，而不只看代码重复

假设练习计划需要选题策略。计划**使用**选题器，但计划本身不是选题器：

```java
import java.util.List;
import java.util.Objects;

interface QuestionSelector {
    List<String> select(List<String> questionIds, int count);
}

final class PracticePlan {
    private final int dailyTarget;
    private final QuestionSelector selector;

    PracticePlan(int dailyTarget, QuestionSelector selector) {
        if (dailyTarget <= 0) {
            throw new IllegalArgumentException("每日目标题数必须为正");
        }
        this.dailyTarget = dailyTarget;
        this.selector = Objects.requireNonNull(selector);
    }

    List<String> chooseFrom(List<String> questionIds) {
        return selector.select(questionIds, dailyTarget);
    }
}
```

`PracticePlan` 通过字段组合一个 `QuestionSelector`；不同选题算法可以实现同一接口，创建计划时选择其一。若让 `PracticePlan extends SomeSelector`，计划会变成一种选题器，调用方还能依赖选题器上与计划无关的成员。这样的子类型承诺并不会因为少写几行委托代码就变得合理。

反过来，若调用方确实需要统一处理不同题型，而且每种题型都能满足 `Question` 的行为约定，题型可以实现共同接口或继承为扩展而设计的抽象基类。选择接口还是抽象类、是否需要共享状态，是下一层问题；关键是子类型能否在父类型的使用场景中保持原有承诺。

## 继承的成本是什么

继承把父类的可访问成员纳入子类的类型表面。子类不能挑选其中几个方法继承，也不能在违反父类公开语义的情况下只重写自己感兴趣的部分。若父类提供 `protected` 扩展点、在内部调用可重写方法，子类还会依赖这些调用时机和状态；父类实现变化可能改变子类行为。因此，继承具体类前要看它是否有清楚、稳定的扩展契约，而不能只看当前实现是否方便复用。

组合把对协作者的依赖留在实现内部，外层类型可以只公开自己的操作。不过组合不会自动获得协作者的多态能力；如果外层对象也必须被当作某个接口使用，就需要显式实现该接口并完成相应委托。

两者也可以同时出现。Java 17 的 `FilterInputStream` **继承** `InputStream`，所以仍可传给接受输入流的代码；它又**持有**另一个 `InputStream`，把读取操作委托给底层流，供子类在此基础上增加功能。这说明是否采用继承由对外类型契约决定，是否采用组合由内部如何完成工作决定。
