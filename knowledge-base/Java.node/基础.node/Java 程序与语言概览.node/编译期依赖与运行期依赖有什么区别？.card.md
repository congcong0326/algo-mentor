编译期依赖和运行期依赖解决的是两个不同问题：编译器需要依赖来检查源码、生成字节码；JVM 需要依赖来加载类、解析方法和执行代码。Maven 项目中，某个依赖出现在编译 classpath，并不自动保证它会出现在最终运行环境的 classpath。

因此，“`mvn package` 成功”只能说明构建阶段所需的类可用；应用能否启动，还要看最终 JAR、容器或启动脚本是否携带了运行期需要的依赖。

## 两个阶段分别做什么

编译阶段，`javac` 需要找到源码中引用的类型和成员：

```java
import com.example.sdk.Client;

class Service {
    Client client;
}
```

如果编译 classpath 没有 SDK，通常会出现 `package ... does not exist` 或 `cannot find symbol`。

运行阶段，JVM 需要找到实际执行路径上的类。即使 `Service.class` 已经生成，如果运行时没有 SDK，启动或第一次执行相关代码时仍可能出现：

```text
java.lang.ClassNotFoundException: com.example.sdk.Client
```

或：

```text
java.lang.NoClassDefFoundError: com/example/sdk/Client
```

编译器验证的是“源码能否编译”，JVM 验证的是“当前运行路径能否完成类加载和链接”；两者使用的 classpath 可以不同。

## Maven scope 如何影响两个 classpath

常见 scope 可以先按下面的规律理解：

| scope | 编译主代码 | 运行主代码 | 打包进常见 Spring Boot 可执行 JAR |
| --- | --- | --- | --- |
| `compile`（默认） | 是 | 是 | 通常是 |
| `runtime` | 否 | 是 | 通常是 |
| `provided` | 是 | 通常由运行环境提供 | 通常否 |
| `test` | 只对测试代码 | 只对测试运行 | 否 |
| `system` | 是 | 取决于外部路径 | 不建议使用 |

例如，JDBC 驱动常常只在业务代码不直接引用其 API、但运行时需要具体实现时使用 `runtime`；Servlet API、某些容器提供的 API 可以使用 `provided`。具体项目仍要结合框架和部署方式确认，不能只根据依赖名称判断。

`runtime` 依赖不会进入主代码的编译 classpath，因此业务代码不能直接引用它的类型；但它会进入运行 classpath。`provided` 依赖能帮助代码编译，但构建工具通常假定部署平台会提供它，不会把它复制进应用制品。

## Spring Boot 项目中的典型情况

以本项目的 `mentor-api` 为例，`spring-boot-maven-plugin` 会把需要随应用交付的运行依赖放进：

```text
BOOT-INF/lib/
```

业务 class 放进：

```text
BOOT-INF/classes/
```

执行 `java -jar app.jar` 时，Boot Launcher 会组装这些内容。如果某个依赖被标记为 `provided`，或者被插件排除，它可能仍能让 Maven 编译成功，却不会出现在 `BOOT-INF/lib`，部署后就可能失败。

反过来，测试依赖通常只服务于 `src/test`。测试能运行不代表生产应用拥有这些类；不能把测试 classpath 当成生产运行 classpath。

## 常见的“编译成功、运行失败”原因

1. 依赖使用了 `provided` 或 `test` scope，但生产环境没有实际提供。
2. 依赖被标记为 optional，当前应用没有显式声明它，但代码或配置实际需要它。
3. 打包插件排除了某个库，或只复制了业务 JAR，没有复制依赖。
4. 启动脚本的 `-cp` 只包含业务目录，没有包含依赖目录或 JAR。
5. 本地 IDE 自动加入了依赖，容器或服务器的启动命令没有加入。
6. 依赖版本冲突导致类能找到，但缺少所需的方法或字段，进一步出现 `NoSuchMethodError`、`NoSuchFieldError` 等链接错误。
7. 依赖只在某个 Maven profile 中声明，构建和部署使用了不同 profile。

## 如何检查最终运行时 classpath

不要只查看 `pom.xml`，应检查实际构建结果和启动方式：

```sh
# 查看 Spring Boot JAR 中是否包含依赖
jar tf target/*.jar | grep 'BOOT-INF/lib/'

# 查看 Maven 解析出的依赖及 scope
mvn dependency:tree

# 查看更接近运行时的依赖集合
mvn dependency:build-classpath -Dmdep.outputFile=runtime-classpath.txt
```

还要确认：

- 最终启动的是哪个 JAR；
- 使用的是 `java -jar` 还是自定义 `-cp`；
- 依赖是否被打进 `BOOT-INF/lib`，或由部署环境提供；
- 是否有多个版本的同名依赖；
- 运行容器、IDE 和本地 shell 是否使用了不同的启动配置。

## 面试回答框架

可以这样回答：

> 编译期依赖用于让编译器解析源码中的类型和方法，运行期依赖用于让 JVM 在加载、链接和执行字节码时找到所需类。Maven 的 scope 会影响依赖进入哪些 classpath；`provided` 和 `test` 依赖尤其容易导致“编译成功、运行失败”。在 Spring Boot 中，最终应检查依赖是否进入 `BOOT-INF/lib`，以及实际启动命令是否通过 Boot Launcher 或 `-cp` 把它们加入运行路径。
