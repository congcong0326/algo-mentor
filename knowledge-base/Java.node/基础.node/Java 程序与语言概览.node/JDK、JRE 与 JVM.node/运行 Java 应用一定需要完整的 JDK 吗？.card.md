运行已经编译好的 Java 应用，通常不需要完整 JDK，只需要满足应用需求的 JVM、标准类库和运行支持，并提供应用自身及第三方依赖。可以选择完整 JDK、厂商提供的 JRE／运行时发行包，或使用 `jlink` 制作定制运行时。

如果应用需要在运行时编译 Java 源码，或者运维需要特定诊断工具，就必须额外提供相应能力。选择依据是**应用的运行需求和运维需求**，不能仅凭“程序能启动”判断环境是否足够。

## 构建环境与运行环境承担不同工作

以 Java 17 为背景，一个常见的交付流程是在构建机器上编译、测试并打包，再将产物交给服务器运行。

| 阶段 | 典型工作 | 环境需求 |
| --- | --- | --- |
| 构建 | 编译源码、运行测试、生成 JAR | 通常需要 JDK 和 Maven、Gradle 等构建工具 |
| 运行 | 启动已经构建好的应用包 | 需要满足应用依赖的 Java 运行环境 |
| 运维诊断 | 查看线程、采集堆信息、分析运行状态 | 需要相应诊断能力，常通过 JDK 工具提供 |

例如，构建阶段执行 `mvn package`，部署阶段启动可执行 JAR：

```sh
java -jar app.jar
```

运行服务器通常不需要再执行 `javac`，也不必安装 Maven。应用包如何携带或定位第三方依赖，取决于具体打包方式；并非任意 JAR 都能直接通过 `java -jar` 启动。

## 除了安装 JDK 或 JRE，还有什么选择

| 选择 | 获得方式 | 适用条件与取舍 |
| --- | --- | --- |
| 完整 JDK | 下载厂商发行包 | 开发和诊断工具较齐全，体积通常也较大 |
| 现成 JRE／运行时发行包 | 下载提供此类产品的厂商发行包 | 需要确认具体包含哪些模块和工具 |
| 定制运行时 | 使用 JDK 中的 `jlink` 生成 | 按需包含模块，但需要维护依赖配置、测试和安全更新流程 |

定制运行时在职责上仍是一套 Java 运行环境，可以理解为针对应用组装的 JRE。区别在于它不一定是厂商统一提供的安装包，而是由应用发布者制作并交付。

例如，在安装了完整 JDK 17 的构建机器上，为仅依赖 `java.base` 的程序生成运行环境：

```sh
jlink --add-modules java.base --output app-runtime
```

生成目录中包含自己的 `bin/java`、JVM 和所选模块的运行支持，可以用它启动已经编译好的 `Hello.class`：

```sh
./app-runtime/bin/java -cp . Hello
```

这个示例只适用于依赖由 `java.base` 满足的程序。真实应用需要根据自身依赖选择模块。

**`jlink` 主要负责生成运行时，不会自动把任意应用 JAR 及其第三方依赖全部打包进去。** 对普通 classpath 应用，可以将定制运行时、应用包、第三方依赖和启动脚本一起交付：

```text
app/
├── app-runtime/
├── app.jar
├── lib/
└── start.sh
```

启动脚本明确调用随应用交付的 `app-runtime/bin/java`。目标机器因此无需另外安装 JDK 或 JRE，但仍需满足这套运行时的操作系统和原生库要求。

完整 JDK 和现成运行时也可以随应用分发。运行环境的组成，以及由用户安装还是随应用交付，是两个独立的选择。

## 定制运行时还具有跨平台能力吗

Java 的跨平台能力主要体现为：同一份兼容的字节码，由各平台对应的运行环境执行。JVM、启动器和原生库本身是平台相关的，完整 JDK、JRE 和定制运行时都需要匹配目标平台。

对于没有平台专用依赖、且运行时版本兼容的应用，可以这样交付：

```text
同一个 app.jar + Linux x64 运行时   → Linux x64 交付包
同一个 app.jar + Windows x64 运行时 → Windows x64 交付包
同一个 app.jar + macOS ARM64 运行时 → macOS ARM64 交付包
```

因此，定制运行时本身不能直接跨操作系统或 CPU 架构使用，但不意味着 Java 字节码失去了跨平台能力。

制作运行时也不一定必须在目标操作系统上完成。`jlink` 可以使用目标平台 JDK 的 JMOD 文件进行跨平台链接，但需要匹配工具和模块版本，并满足相关限制；不能拿当前平台的组件就期待生成另一个平台的运行时。实际交付中，在各目标平台的 CI 环境分别构建、测试，通常更容易维护。

无论在哪个平台生成，都需要在目标平台验证。除操作系统和 CPU 架构外，还要考虑系统版本、Linux 的 glibc 与 musl 差异，以及应用使用的 JNI 原生库等条件。

随应用交付定制运行时，相当于将平台适配的责任，从“用户安装正确的 JRE”转移到了“发布者提供正确的平台包”。

## 哪些场景需要额外的工具能力

运行时编译 Java 源码是典型情况，例如应用通过 `JavaCompiler` 编译动态生成的代码，或某些规则引擎、JSP 容器先生成 Java 源码再编译。

这些场景需要的是**编译器能力**，不一定必须部署完整 JDK。有的实现自带编译器；使用定制运行时，也可以包含相应编译器模块。以 JDK 自带实现为例，只有编译器 API 所在的 `java.compiler` 模块并不代表已有编译器实现，还需要 `jdk.compiler` 等相应支持。没有系统编译器可用时，`ToolProvider.getSystemJavaCompiler()` 可以返回 `null`。

反射、动态代理和直接生成字节码，本身不等于编译 Java 源码，不能据此推断必须安装完整 JDK。

运维方面，应用能够运行，并不代表环境中一定提供了 `jcmd` 等计划使用的工具。即使工具存在，还需要满足版本、权限和进程访问等条件，才能完成诊断。

## 如何判断运行环境是否足够

启动成功可能只是尚未执行到缺少能力的代码路径。某个请求才触发动态编译，某项业务才访问被裁掉的模块，或者故障发生后才需要诊断工具，都可能暴露环境缺口。

`jdeps` 可以辅助分析静态依赖，但反射、服务发现、动态加载等路径需要结合应用配置和实际测试确认。验证应覆盖主要业务路径、动态功能以及预定的诊断流程。

对于一般后端服务，完整 JDK 是便于保留常用工具的起点；有明确体积要求时，再评估运行时发行包或定制运行时。自行交付运行环境后，也要负责跟进安全更新、重新构建和发布，不能只更新应用 JAR。

Docker 镜像是交付方式，镜像内仍需要相应运行环境。GraalVM Native Image 则是另一条路线：提前将应用编译为本地可执行文件，部署时通常无需额外安装 Java 运行环境，但需要遵守其构建要求和兼容性约束，不属于普通 JAR 配合 JVM 的运行方式。
