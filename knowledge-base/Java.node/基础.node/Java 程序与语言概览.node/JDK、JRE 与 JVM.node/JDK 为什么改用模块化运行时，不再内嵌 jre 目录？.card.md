从 JDK 9 开始，JDK 改用模块化运行时映像，不再沿用 JDK 8 中“JDK 内嵌一个完整 `jre/` 目录”的布局。JDK 17 延续了这套设计。变化的核心不是简单删除一个目录，而是把运行环境组织为一组模块及其依赖，并用统一的运行时映像保存这些模块、JVM 和其他运行支持。

这样做是为了让 Java 平台更容易按需裁剪、维护和演进，也减少工具对 `rt.jar`、`tools.jar` 等内部文件布局的依赖。完整 JDK 仍然可以直接运行 Java 程序；没有独立的 `jre/` 目录，不代表没有 Java 运行环境。

## JDK 8 的布局有什么局限

JDK 8 的典型布局大致如下：

```text
JDK 8
├── bin/
│   ├── java
│   └── javac
└── jre/
    ├── bin/
    └── lib/
        └── rt.jar
```

JDK 镜像在自己的 `jre/` 子目录中嵌入运行环境，平台类库主要放在 `rt.jar` 等文件中。这套布局能够运行程序，但随着 Java 平台和工具链变复杂，逐渐暴露出几个问题：

- 应用需要的功能不同，却通常要携带一套完整运行环境，难以按依赖裁剪。
- 类和资源集中在大 JAR 中，不利于按模块定位、组合和后续扩展。
- 配置文件、公开可依赖的文件和实现内部文件混在传统目录中，边界不清晰。
- 一些 IDE、扫描器和脚本直接打开 `rt.jar`、`tools.jar`，绑定了本应属于实现细节的文件布局。

## 模块化运行时解决了什么

JDK 9 引入模块系统，并重新组织 JDK 和 JRE 的运行时映像。以常见的 Linux HotSpot JDK 17 为例，相关目录如下；具体文件名和位置可能因平台、实现而不同：

```text
JDK 17
├── bin/
│   ├── java
│   └── javac
├── conf/
├── lib/
│   ├── modules
│   └── server/
│       └── libjvm.so
└── jmods/
```

这些目录的职责不同：

- `bin/` 放置由映像中的模块提供的启动器和开发工具。
- `conf/` 放置面向开发者、部署者或最终用户的配置文件。
- `lib/` 保存运行时库和实现文件，例如 Linux HotSpot 常见的 `libjvm.so`；其中许多文件属于内部实现，文件名和格式不应被外部工具硬编码依赖。
- `lib/modules` 保存运行时使用的模块化类和资源，其内部格式属于实现细节。
- `jmods/` 保存供链接工具使用的 JMOD 文件，不是运行时加载类库的目录。

平台类和资源不再依赖 `rt.jar`、`tools.jar` 这样的历史内部 JAR。运行时映像以模块为单位组织内容，工具可以通过受支持的 `jrt:/` 协议访问映像中的模块、类和资源，而不需要知道底层存储格式。

因此，**收益来自模块化和运行时映像设计，单纯删除或移动 `jre/` 目录不会带来这些收益。**

## 为什么不继续保留“JDK 包着 JRE”

模块化之后，可以把一个 Java 运行环境理解为：一组模块及其依赖，加上运行这些模块所需的 JVM 和其他支持文件。

完整 JDK 是包含完整开发工具的运行时映像；应用专用运行环境则可以只包含应用需要的模块。两者可以采用统一的组织方式，不必继续维护“先准备完整 JRE，再在外面套开发工具”的固定目录层次。

例如，一个只使用基础语言和标准工具类的小程序可能只需要 `java.base`；使用 JDBC 的程序还需要 `java.sql` 及其依赖。`jlink` 可以根据模块依赖构建定制运行时映像：

```sh
jlink \
  --module-path "$JAVA_HOME/jmods" \
  --add-modules java.base,java.sql \
  --output app-runtime
```

示例只说明机制，实际应用还需要根据自身模块、启动方式和运行期动态加载行为确定依赖。

## 新设计是否更优秀

在按需部署、平台维护和实现演进方面，模块化运行时更有优势，但它不是所有场景下都自动更优：

| 方面 | 模块化运行时的变化 | 需要承担的代价 |
| --- | --- | --- |
| 部署体积 | 可以按实际依赖构建较小的运行时 | 直接安装完整 JDK 时不会自动获得裁剪收益 |
| 维护边界 | 模块依赖更明确，配置与内部实现分离 | 依赖旧目录或内部文件的工具需要迁移 |
| 存储与工具 | 运行时映像可以演进，工具可通过 `jrt:/` 访问 | 读取 `rt.jar`、`tools.jar` 的旧工具可能失效 |
| 安全与交付 | 可只交付应用所需模块，减少不必要组件 | 定制运行时的安全更新需要重新构建和发布 |

`jlink` 也不是无条件的优化。反射、服务发现、动态加载等代码路径可能不会完整体现在简单的静态依赖分析中，裁剪前需要验证实际运行场景。是否使用定制运行时，应结合镜像体积、诊断工具需求、依赖完整性和维护成本决定。

新的运行时存储格式以更高效地保存和读取类、资源为目标，但这不意味着所有业务都会启动更快、吞吐量更高；具体性能收益仍需测量。

## 对日常开发和部署的影响

普通 Java 项目的编译和运行方式基本延续：仍然可以使用 `javac`、`java -jar`、Maven 和传统 classpath；业务项目也不必因为 JDK 自身模块化就立即编写 `module-info.java`。

需要调整的是依赖运行时内部布局的脚本和工具：

- 启动命令应使用 `$JAVA_HOME/bin/java`，不再硬编码 `$JAVA_HOME/jre/bin/java`。
- 不应通过查找 `rt.jar` 或 `tools.jar` 判断 JDK 是否完整。
- 读取 JDK 配置时应检查新的 `conf/` 目录，并优先使用公开 API 或工具接口。
- 对于后端服务，可以继续使用完整 JDK 或现成运行时发行版；只有在确有体积或隔离需求时，再评估 `jlink`。

所以，“JDK 17 没有独立的 `jre/` 目录”只说明安装布局变化；“Java 程序仍需要运行环境”说明 JVM、标准类库和运行支持依然必要；“某个厂商不再提供独立 JRE 下载”则是产品分发选择。这三句话描述的是不同层面，不能混为一谈。
