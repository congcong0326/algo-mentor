LTS 是 Long-Term Support，即长期支持。Java 的 LTS 版本通常由发行商或维护组织在较长时间内持续提供安全更新和缺陷修复，让应用可以在同一个功能版本上维护多年。

非 LTS 版本也是正式发布的版本，可以用于生产；主要区别是维护窗口通常较短，使用者需要更频繁地升级，才能持续获得更新。

**LTS 表示长期维护安排，不额外保证程序兼容，也不意味着可以停止安装补丁。** 具体支持多久、覆盖哪些平台、更新是否免费以及是否提供商业技术支持，都要核对所选 JDK 发行版的政策，不能只看 Java 版本号。

## 长期支持支持的是什么

Java 按固定节奏发布新的功能版本，现代发布节奏通常为每六个月一次。发行商会选择其中一些版本提供长期维护，例如 Java 17 是广泛获得长期支持的版本。

在后续功能版本发布后，维护者仍会为受支持的 Java 17 版本线提供更新，将适用的安全补丁和缺陷修复回移到该版本线。应用因此可以继续使用 Java 17，同时安装新的 `17.0.x` 更新。

这里要区分两种升级：

| 升级方式 | 主要目的 |
| --- | --- |
| Java 17 的旧更新版本升级到较新的 `17.0.x` | 在同一功能版本上获得安全补丁和缺陷修复 |
| Java 17 升级到 Java 21 等更高功能版本 | 迁移到新的平台版本，获得新的语言、API 和运行时能力 |

长期维护不意味着会把后续版本的所有新特性加入 Java 17，也不意味着最初安装的 Java 17 二进制文件会自动得到修复。应用需要实际更新所使用的 JDK 或运行时，并完成必要的验证。

## LTS 与非 LTS 的实际区别

| 方面 | LTS 版本 | 非 LTS 版本 |
| --- | --- | --- |
| 发布性质 | 正式发布版本 | 同样是正式发布版本 |
| 维护窗口 | 通常为多年，取决于发行版政策 | 通常较短，常见为到下一个功能版本发布为止 |
| 升级节奏 | 可以较长时间保留同一功能版本，持续安装更新 | 需要更频繁地迁移到后续功能版本，以继续获得更新 |
| 适用情况 | 希望减少功能版本迁移频率、维护周期较长的系统 | 能够持续升级，并希望较早使用新能力的系统 |

非 LTS 不等于测试版。预览特性是另一项独立概念：LTS 和非 LTS 的正式发行版本都可能包含需要显式启用的预览特性，不能通过 LTS 标签判断某项语言特性是否已经定稿。

## 为什么必须同时看发行版

“Java 17 是 LTS”没有完整回答“我们使用的 Java 17 还能获得多久的更新”。实际维护安排由提供发行包或支持服务的组织决定。

例如，Oracle JDK 和 Eclipse Temurin 都提供 Java 17 发行包，但不能将 Oracle 的支持截止日期、许可条件或商业服务承诺直接套用到 Temurin。

选择时需要分别确认：

- **维护期限与平台范围**：所用功能版本、操作系统和 CPU 架构是否仍在维护范围内。
- **更新获取方式与许可**：补丁从哪里获取，实际使用场景是否满足发行包的许可条件。
- **技术支持服务**：公开提供更新包，与承诺故障响应时间的商业支持是两回事。

这些政策可能调整，应以对应发行版的支持路线图和条款为准。LTS 标签本身不能推出“永久免费更新”或“必须付费”。

## LTS 是否意味着更兼容

LTS 标签不会提供额外的源码、二进制或行为兼容保证。Java 平台的兼容性规则与具体版本变更，仍然需要单独判断。

例如，从 Java 11 迁移到 Java 17，即使两个版本都属于 LTS，也不能省略对依赖、反射访问边界和启动配置的验证。同一个 LTS 版本内的安全更新也可能调整安全限制或修复旧行为，关键业务仍需要回归验证。

选择 LTS 的主要收益是可以减少跨功能版本迁移的频率，为升级和测试安排更充裕的时间；不能仅凭这个标签认定它一定比非 LTS 版本缺陷更少或性能更好。

## 放到项目中如何理解

以采用 Java 17 的 algo-mentor 为例，版本维护至少包含两项工作：

- 明确开发、构建和部署所用的 JDK 发行版及完整更新版本，持续安装仍受维护的 Java 17 更新。
- 根据发行版维护期限、依赖支持范围和业务需要，规划迁移到后续功能版本，并验证构建、测试和实际运行情况。

“项目使用 Java 17 LTS”可以说明功能版本选择，但还不足以说明运行环境已经及时修补，或未来几年一定能免费获得所需支持。
