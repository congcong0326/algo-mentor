# 记忆摘要的主流实现思路与方案对比

更新时间：2026-07-14

> 关联阅读：[[记忆系统的定位与主流框架设计对比]]、[[记忆系统的四段生命周期与业界通用设计法]]。
>
> 本文聚焦跨会话、面向用户画像的 **Memory Summary（记忆摘要）如何实现**。暂不讨论数据库字段、具体存储选型，也不在本篇决定 algo-mentor 应采用哪一种方案。

本文所说的“主流做法”，是指在产品、框架和论文中反复出现的工程范式，并非正式行业标准。这些范式也不一定互斥：有的决定内部状态如何保存，有的决定摘要如何组织或在什么时候生成，生产系统通常会组合使用。

## 一、先明确本文讨论的 Memory Summary

“记忆摘要”在不同系统里可能指三种不同东西：

1. **对话滚动摘要**：为了压缩当前会话上下文，把较早消息总结成一段短文本。
2. **内部用户画像**：系统长期维护的用户偏好、目标、状态和经历的综合表示。
3. **用户可见的记忆摘要**：把内部记忆以较易理解的形式展示给用户，并允许用户纠正、抑制或删除。

本文主要讨论第 3 种，同时必须关注第 2 种，因为一个关键问题是：

> 用户看到的摘要，本身是系统唯一的记忆状态，还是内部记忆状态的一种派生视图？

这两种定位会产生完全不同的更新、纠错和删除机制。

为了避免混淆，可以先把一个完整系统拆成四层：

```text
原始来源层        聊天、文件、业务事件、用户显式输入
       │
       ▼
内部记忆层        系统实际保存和持续更新的记忆状态
       │
       ├──────────────▶ 用户可见的 Memory Summary
       │                         （管理视图）
       │
       └──▶ 本轮相关记忆选择 ──▶ 运行时上下文 ──▶ LLM
```

因此在成熟系统中，下面三者通常不应直接画等号：

```text
用户可见摘要 ≠ 内部完整记忆 ≠ 本轮实际注入模型的上下文
```

## 二、ChatGPT 当前产品行为提供了什么线索

截至 2026-07-14，OpenAI 的 Memory FAQ 对新版 Memory Summary 公开了以下产品行为：

- 记忆会根据聊天、文件和连接应用中的上下文持续更新。
- Memory Summary 只展示系统认为重要的高层信息，不包含系统记住的全部内容。
- 用户可以通过自然语言修改摘要，也可以选中局部内容进行纠正。
- “Don't mention this again”表示今后尽量不再主动引用，但不等于删除原始信息。
- 用户可以查看部分用于个性化回答的来源，但来源列表不保证展示所有影响因素。
- 系统只在认为个性化有帮助时才搜索历史，而不是每次请求都搜索。
- 旧版 Saved Memories 仍作为 legacy 机制保留，因此新版 Memory Summary 不是旧版条目列表的简单改名。

公开资料没有披露 ChatGPT 内部的数据结构、摘要模型或检索算法，不能据此断言它一定使用某种数据库或向量检索方案。但这些产品行为至少说明，一个完整的 Memory Summary 需要处理：

- **持续更新**，而不是一次性生成；
- **摘要不完备**，内部记忆范围可能大于展示内容；
- **用户修改**，修改需要反映到后续个性化；
- **抑制与删除分离**；
- **来源关联**，摘要或回答能够回到部分原始证据；
- **摘要与按需检索协作**，而不是只依赖一段固定文本。

下面的方案预研讨论如何实现这些能力，但不把它们当成 ChatGPT 内部实现的事实。

## 三、方案一：单一滚动摘要

### 3.1 核心思路

系统只维护一份摘要文本。每积累若干条新消息，就把“旧摘要 + 新消息”交给 LLM，生成一份新摘要：

```text
新摘要 = summarize（旧摘要，新产生的对话）
```

更新可以按不同条件触发：

- 每轮对话后更新；
- 每累计若干轮更新；
- 上下文达到 token 阈值后更新；
- 会话结束后统一更新。

LangGraph 的 `Summarize messages` 就是这一模式的典型实现：保留已有 running summary，用新消息扩展摘要，并删除已经被摘要覆盖的旧消息。

### 3.2 优点

- 实现最简单，只有一份需要维护的状态。
- 摘要可以直接注入 prompt，不需要额外检索。
- token 成本和存储成本容易估算。
- 很适合解决单个长会话的上下文压缩问题。

### 3.3 主要问题

**第一，摘要会发生累积性信息损失。**

每次更新都在上一次压缩结果上继续压缩。某个细节一旦被上一轮丢掉，后续通常无法自行恢复。长期运行后还可能出现摘要漂移：表达越来越概括，甚至逐渐偏离原始语义。

**第二，冲突处理完全隐藏在摘要生成里。**

当新旧信息矛盾时，模型可能覆盖旧结论、同时保留两种说法，或者错误地把二者合并。系统很难解释发生了什么。

**第三，用户管理能力较弱。**

用户修改一句话，本质上是在编辑整份唯一状态。系统难以判断这次修改是在纠正某个事实、要求以后不要提及，还是要求删除所有相关来源。

**第四，难以溯源和重建。**

如果原始消息已经被删除，摘要中的一句话很难再定位到具体证据；如果保留全部原始消息，又削弱了这一方案“只有一份简单状态”的优势。

### 3.4 适用范围

单一滚动摘要更适合：

- 当前会话的上下文压缩；
- 历史规模较小的原型；
- 对用户纠错、删除和溯源要求不高的场景。

它可以作为 Memory Summary 的最小实现，但不太适合作为长期、可管理用户记忆的唯一事实源。

## 四、方案二：单一结构化画像文档

### 4.1 核心思路

系统维护一份边界明确的用户 Profile。它可以是结构化 JSON，也可以是带固定章节的文档。新对话到来后，不是重新总结全部历史，而是根据新证据对现有 Profile 做局部修改。

典型更新过程是：

```text
当前 Profile + 新对话
          │
          ▼
LLM 生成局部 Patch
          │
          ▼
校验 Patch ──▶ 应用修改 ──▶ 得到新版 Profile
```

LangGraph / LangMem 将其称为 Profile 模式。其 memory template 进一步区分了“整份重写”和“Patch 更新”：整份重写容易遗漏旧信息，JSON Patch 只修改受新证据影响的局部内容，信息损失相对更小。

### 4.2 优点

- 系统始终有一份完整、边界明确的用户画像。
- 用户查看和修改整份画像比较自然。
- 固定结构可以约束 LLM，减少摘要格式漂移。
- 不需要在每次使用时检索大量零散记忆。
- 采用 Patch 后，更新成本通常低于整份重新生成。

### 4.3 主要问题

**第一，必须预先知道要长期维护哪些信息。**

Profile 越结构化，越依赖提前定义的业务边界。未被结构覆盖的信息可能无法进入摘要，或者只能塞进模糊的自由文本区域。

**第二，Profile 变大后更新仍会变难。**

模型需要理解当前 Profile、找到正确位置并生成合法修改。随着画像变长，错误 Patch、错误覆盖和并发更新冲突都会增加。

**第三，历史演化容易被压平。**

单一 Profile 通常强调“用户现在是什么状态”。它擅长维护当前结论，但不天然擅长表达一个结论从何时开始、经历过哪些变化以及为什么发生变化。

**第四，摘要与事实源仍可能混在一起。**

如果 Profile 中既包含内部状态，又直接承担用户展示和 prompt 注入，三种用途会相互制约：适合机器更新的结构未必适合用户阅读，适合用户阅读的文字也未必适合精确更新。

### 4.4 适用范围

单一 Profile 更适合：

- 业务范围清楚、需要维护的信息类型相对稳定；
- 强调用户当前状态，而不是完整历史演化；
- 希望以较低复杂度提供可查看、可修改的长期画像；
- 可以接受通过业务约束限定“什么值得进入摘要”。

## 五、方案三：原子记忆集合 + 摘要投影

### 5.1 核心思路

系统不把一段摘要作为唯一事实源，而是把每条值得长期保留的信息作为相对独立的记忆单元。Memory Summary 是根据当前有效记忆生成的派生视图，也可以理解为一种 materialized view。

```text
新对话
  │
  ▼
抽取候选记忆
  │
  ▼
与已有记忆比较
  │
  ├── 新增
  ├── 更新或补充
  ├── 取代旧记忆
  └── 无需变化
  │
  ▼
当前有效记忆集合
  │
  ▼
编译 / 生成 Memory Summary
```

Mem0 的长期记忆方案、LangGraph 的 Collection 模式都属于这一类思路：从对话中抽取可复用的信息，保存为可独立搜索和更新的记忆，再根据需要进行检索或组合。

### 5.2 摘要如何生成

摘要生成通常有三种做法：

1. **模板编译**：按既定分类选择当前有效记忆，确定性地生成摘要。
2. **LLM 综合**：把选中的记忆交给模型，生成自然、连贯的用户画像。
3. **混合方式**：关键结论用确定性规则组织，其余内容由 LLM 压缩和润色。

摘要可以在记忆发生变化后立即重建，也可以异步刷新；还可以只在用户打开管理页面或运行时真正需要时再生成。

### 5.3 用户修改如何生效

这一方案里，用户修改 Memory Summary 不应简单覆盖摘要文本，而应被解释为对底层记忆集合的操作：

```text
用户修改摘要
      │
      ▼
识别受影响的底层记忆
      │
      ▼
修改 / 取代 / 抑制 / 删除
      │
      ▼
重新生成摘要
```

难点在于，一句摘要可能综合了多条记忆。一旦用户直接改写这句话，系统需要判断修改应作用于哪几条记忆；判断不清时，应避免静默修改错误的底层状态。

### 5.4 优点

- 摘要可以随时从底层记忆重新生成，不容易因反复压缩而永久丢失信息。
- 便于处理重复、矛盾、过期和状态演化。
- 用户可以管理具体记忆，摘要只承担展示职责。
- 容易保留来源关系，支持解释“为什么系统形成了这个结论”。
- 可以针对不同页面或任务生成不同粒度的摘要。

### 5.5 主要问题

- 写入链路明显更复杂，需要抽取、去重、冲突判断和摘要重建。
- LLM 容易过度抽取，产生大量价值不高的碎片。
- 同一件事可能被拆得过细，导致摘要缺少整体语境。
- 底层记忆更新和摘要刷新通常是最终一致，短时间内可能不同步。
- 用户修改自然语言摘要时，需要一个可靠的“摘要修改 → 底层记忆操作”翻译过程。

### 5.6 适用范围

原子记忆集合 + 摘要投影更适合：

- 记忆会长期积累并持续变化；
- 用户需要查看、纠正和删除具体内容；
- 需要处理矛盾、过期与历史演化；
- 需要保留来源或支持审计；
- 可以承担较高的写入和整合复杂度。

## 六、方案四：分层 / 分域摘要

### 6.1 核心思路

系统不维护一份无限增长的全局摘要，而是按会话、主题、时间或业务领域维护多级摘要：

```text
原始消息
   │
   ▼
会话摘要 / Episode Gist
   │
   ▼
主题或领域摘要
   │
   ▼
全局用户摘要
```

ReadAgent 的 gist memory 提供了相似思路：先把长内容划分为 episode，再生成短 gist；模型需要细节时，可以根据 gist 回到原始片段。MemoryBank 等长期记忆系统也采用过“事件摘要 + 用户画像持续更新”的组合。

### 6.2 更新方式

当底层内容变化时，可以采用三种传播策略：

- **立即向上更新**：叶子摘要变化后，立刻重算主题和全局摘要。
- **延迟批量更新**：先记录底层变化，定时重建上层摘要。
- **按需更新**：读取某个上层摘要时，发现版本落后再重新生成。

### 6.3 优点

- 能支撑很长的历史和多个信息来源。
- 全局摘要保持简短，同时保留向下查找细节的路径。
- 不同领域可以独立更新，减少无关内容相互干扰。
- 某一层摘要质量不足时，仍有机会回到下层摘要或原始来源。

### 6.4 主要问题

- 下层变化如何可靠传播到上层，是实现中的核心难点。
- 同一信息可能同时出现在多个主题中，容易产生重复和不一致。
- 多层 LLM 摘要仍然可能放大信息损失或错误。
- 用户编辑全局摘要后，需要确定修改应落到哪个领域或哪一层。
- 摘要层级、主题划分和重建频率都需要持续调优。

### 6.5 适用范围

分层 / 分域摘要更适合：

- 用户历史非常长，单一 Profile 已难以维护；
- 信息明显分布在多个领域；
- 既要全局画像，也要能够下钻到具体经历；
- 可以接受较复杂的异步更新和版本管理。

## 七、方案五：检索增强的即时摘要

### 7.1 核心思路

系统不预先维护一份完整的全局摘要，或者只维护一份非常薄的核心摘要。每当发生具体请求时，先判断是否需要个性化信息，再检索相关历史，临时合成本轮需要的“工作摘要”：

```text
当前问题
   │
   ▼
是否需要个性化上下文
   │
   ▼
检索相关历史 / 记忆
   │
   ▼
生成本轮即时摘要
   │
   ▼
注入 LLM
```

ChatGPT 当前公开的产品行为已经明确包含“只在可能改善回答时搜索历史”，但没有公开具体使用的是关键词、向量、业务过滤还是多路混合检索。

### 7.2 优点

- 每次只组织与当前问题相关的信息，prompt 利用率高。
- 不需要频繁重写一份全局摘要。
- 新信息进入索引后可以较快参与后续回答。
- 对长尾细节和具体历史事件的利用能力较强。

### 7.3 主要问题

- 摘要质量首先受检索召回质量限制；没有检索到的信息无法参与合成。
- 每次请求可能增加检索、重排和摘要生成延迟。
- 相同用户在不同问题下得到的“即时画像”不同，不适合作为稳定的用户管理视图。
- 用户很难查看和管理系统所有可能检索出的信息。
- 如果只依赖即时摘要，系统缺少一份稳定、可审阅的长期认识。

### 7.4 适用范围

即时摘要更适合：

- 作为稳定 Memory Summary 的补充读取机制；
- 历史规模很大、每次只需要其中很小一部分；
- 强调任务相关性而不是固定全局画像；
- 可以接受一定的请求时延和结果波动。

它解决的主要是“本轮该想起什么”，而不是“用户应该如何查看系统长期记住了什么”。

## 八、五种方案并不是同一维度的互斥选项

表面上看，上述五种方案都在生成摘要，实际上它们分别回答了不同问题：

| 设计问题 | 常见选择 |
|---|---|
| 什么是内部事实源 | 单一摘要 / 单一 Profile / 原子记忆集合 / 原始历史 |
| 如何更新现有状态 | 整份重写 / 局部 Patch / 记忆级新增与取代 |
| 如何组织大规模历史 | 扁平 / 分域 / 分层 |
| 何时形成摘要 | 对话热路径 / 后台异步 / 定时 / 用户触发 / 按需生成 |
| 本轮如何使用记忆 | 注入完整摘要 / 选择部分摘要 / 检索后即时合成 |

所以真实生产系统往往是组合方案，例如：

```text
原子记忆集合作为事实源
+ 分域摘要作为长期管理视图
+ 检索增强即时摘要作为运行时上下文
```

也可能采用更轻的组合：

```text
结构化 Profile 作为当前画像
+ 原始历史检索补充长尾细节
```

后续讨论“哪种方案适合 algo-mentor”时，更准确的方式不是从五个名称中单选，而是分别确定状态表示、更新方式、组织层级、生成时机和读取方式。

## 九、方案对比

| 方案 | 摘要是否承担事实源 | 信息损失风险 | 冲突与纠错能力 | 用户管理能力 | 主要成本或风险 |
|---|---|---|---|---|---|
| 单一滚动摘要 | 是 | 高，反复压缩会累积 | 弱 | 弱 | 摘要漂移、不可溯源 |
| 单一结构化 Profile | 通常是 | 中，Patch 可降低风险 | 中 | 中到高 | 依赖预定义边界，画像变大后难更新 |
| 原子记忆 + 摘要投影 | 否 | 低到中，可从底层重建 | 强 | 强 | 抽取、整合和一致性复杂 |
| 分层 / 分域摘要 | 视实现而定 | 中，多层传播可能放大误差 | 中到强 | 中 | 层级同步和跨域一致性复杂 |
| 检索增强即时摘要 | 否 | 取决于检索召回 | 中 | 弱，不适合全局管理 | 请求时延、漏召回和结果波动 |

另一个更实用的理解是：

- **滚动摘要**主要解决上下文压缩；
- **Profile**主要解决当前画像维护；
- **原子记忆集合**主要解决长期演化和精细管理；
- **分层摘要**主要解决规模扩张；
- **即时摘要**主要解决查询相关性。

## 十、后续选型前需要讨论的问题

本篇先不做项目选型。下一步需要围绕以下问题判断，而不是直接讨论数据库或字段：

1. **Memory Summary 是事实源还是管理视图？**
   - 用户修改摘要，是直接修改唯一状态，还是触发底层记忆变化后重新生成？

2. **摘要更强调“当前状态”还是“历史演化”？**
   - 前者更接近 Profile，后者更需要原子记忆或分层 episode。

3. **用户需要管理到什么粒度？**
   - 只修改整份画像，还是能纠正某个结论、抑制某类引用、删除相关来源？

4. **是否要求解释摘要从哪里来？**
   - 如果需要来源和审计，单一滚动摘要很难满足。

5. **摘要需要多快更新？**
   - 对话后立即更新、后台延迟更新、定时更新，还是用户打开页面时再更新？

6. **全局摘要和任务相关记忆如何分工？**
   - 哪些信息长期放在摘要中，哪些信息只在具体问题出现时检索和临时合成？

这些问题收敛后，再讨论 algo-mentor 的适用组合会更有依据。

---

## 十一、阶段性结论

- 单一滚动摘要是最简单的基线，但更像上下文压缩，不是长期可管理 Memory Summary 的完整答案。
- 单一结构化 Profile 是实现稳定用户画像的常见轻量方案，关键改进是局部 Patch，而不是反复整份重写。
- 原子记忆集合 + 摘要投影把“事实维护”和“用户展示”分开，是处理纠错、冲突、过期和溯源时最完整的一类思路，但工程复杂度最高。
- 分层 / 分域摘要不是另一种事实源，而是历史规模扩大后的组织方法。
- 检索增强即时摘要主要服务本轮回答，应视为稳定 Memory Summary 的补充，而不是天然替代品。
- 后续选型更可能是多个机制的组合，而不是从五种方案中机械地选择一个。
