# 记忆系统的预期设计方向与核心决策

更新时间：2026-07-14

状态：方向已确认，具体实现待后续设计

> 关联预研：[[记忆摘要的主流实现思路与方案对比]]、[[记忆系统的四段生命周期与业界通用设计法]]、[[记忆系统的定位与主流框架设计对比]]。
>
> 本文用于确定 algo-mentor 记忆系统的总体方向和核心语义，不涉及代码、接口、数据库、字段、模型 Prompt 或具体框架选型。

## 一、核心结论

algo-mentor 的记忆系统预期采用以下总体方向：

> 以聊天、文件和业务事件作为原始证据输入，以可追溯、可独立演化的原子记忆作为长期内部状态，以 Memory Summary 作为可异步重建的用户管理视图；未来在此基础上增加分域摘要和面向具体任务的按需检索。

这一方向包含六项已经确认的选择：

1. **Memory Summary 是管理视图，不是事实源。**
2. **记忆系统需要表达历史演化，而不只保存当前结论。**
3. **用户能够通过自然语言纠正某个结论。**
4. **摘要中的结论需要能够解释其来源。**
5. **普通记忆形成和摘要刷新可以延迟、异步完成。**
6. **全局摘要与任务相关记忆的具体分工，等业务边界明确后再定义。**

## 二、为什么不把 Memory Summary 当作事实源

Memory Summary 面向用户阅读和管理，需要简短、稳定、容易理解。但内部长期记忆还要处理：

- 同一结论在不同时间发生变化；
- 新旧信息之间的矛盾；
- 用户对某个结论的纠正；
- 结论对应的聊天、文件或业务事件来源；
- 不适合放进全局摘要、但未来可能有用的长尾信息；
- 针对不同任务选择不同记忆的需求。

如果摘要本身就是唯一事实源，这些信息只能被压进同一份文本或结构化画像中。摘要一旦重写，旧结论、变化原因和来源关系就容易丢失。

因此系统需要明确区分：

```text
内部记忆状态      系统长期维护的完整记忆
Memory Summary    面向用户的高层管理视图
运行时上下文       本轮真正提供给模型的相关记忆
```

三者之间的关系是：

```text
Memory Summary ≠ 内部完整记忆 ≠ 本轮运行时上下文
```

Memory Summary 可以根据内部记忆重新生成。内部记忆发生变化时，摘要随之刷新；摘要生成失败或暂时过期时，内部记忆不应丢失。

## 三、原始来源、内部记忆与摘要的分层

预期将记忆系统在概念上划分为四层：

```text
┌──────────────────────────────────────┐
│ 原始证据层                           │
│ 聊天、文件、业务事件、用户显式纠正   │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│ 记忆形成层                           │
│ 识别、归纳、消解重复和矛盾           │
└──────────────────┬───────────────────┘
                   │
                   ▼
┌──────────────────────────────────────┐
│ 内部记忆层                           │
│ 可追溯的原子记忆、当前状态、历史演化 │
└───────────────┬──────────────────────┘
                │
         ┌──────┴─────────┐
         ▼                ▼
┌─────────────────┐  ┌─────────────────┐
│ Memory Summary  │  │ 运行时记忆选择  │
│ 用户管理视图    │  │ 面向当前任务    │
└─────────────────┘  └─────────────────┘
```

### 3.1 原始证据层

聊天、文件和业务事件是形成记忆的证据来源，但不自动等于系统当前认可的事实。

原始内容中可能包含：

- 用户的明确陈述；
- 假设、引用、玩笑和反问；
- 已经过时的信息；
- 对未来的计划，而不是已经发生的事实；
- 与旧信息矛盾的新描述；
- 模型生成但未经用户确认的内容。

因此不能把全部原始聊天直接当成当前用户画像。系统需要先判断哪些内容值得形成记忆，以及新证据对已有记忆意味着什么。

### 3.2 内部记忆层

内部长期状态采用原子记忆集合的思路。每个值得长期维护的结论具有相对独立的生命周期，可以被新增、补充、纠正、取代、抑制或删除。

这里的“原子”不是要求把信息拆成最短句子，而是强调：

> 一条记忆应当可以独立判断是否仍然有效、由什么证据形成、是否被新结论取代，以及是否允许在当前场景使用。

内部记忆层负责同时表达：

- 系统当前认可的结论；
- 已经不再是当前状态、但需要保留的历史结论；
- 结论之间的演化关系；
- 结论与原始来源之间的关系。

### 3.3 Memory Summary

Memory Summary 是根据当前内部记忆生成的高层视图，主要服务两个目的：

1. 让用户了解系统当前如何认识自己。
2. 给用户提供纠正、抑制和删除记忆的入口。

它不要求展示所有内部记忆，也不承担完整历史记录的职责。它应优先展示当前重要、对长期个性化有价值、适合用户理解和管理的结论。

### 3.4 运行时上下文

模型在某次任务中真正需要的记忆，不一定等于用户看到的 Memory Summary。

未来的运行时上下文可能由两部分组成：

- 一份较稳定的高层用户摘要；
- 与当前问题相关的原子记忆、历史事件或业务状态。

是否需要全局摘要、分域摘要或按需检索，后续根据具体业务场景决定。当前方向只要求内部记忆能够支持这些读取方式，而不提前固定唯一方案。

## 四、历史演化是记忆系统的一等能力

本系统不只回答“用户现在是什么状态”，还需要在必要时解释“这个状态如何演化而来”。

例如：

```text
较早证据：用户的 NAS 使用 N100
最新证据：用户的 NAS 已更换为 i5-6500
```

系统不应只把摘要中的 `N100` 字样替换为 `i5-6500`，然后丢失旧状态。预期语义是：

```text
旧记忆：NAS 使用 N100
        └── 已被后续结论取代，保留为历史

新记忆：NAS 使用 i5-6500
        └── 当前有效

Memory Summary：用户的 NAS 当前使用 i5-6500
```

这样可以同时满足：

- 当前摘要不再引用过时信息；
- 系统可以解释为什么发生了变化；
- 用户后续再次纠正时，有足够上下文判断是在回退、补充还是描述另一个对象；
- 摘要可以从当前有效记忆重新生成。

普通纠正原则上不等于删除历史。真正的删除是另一种用户意图，需要单独处理。

## 五、用户通过自然语言管理记忆

用户不需要理解内部记忆结构，也不直接编辑底层记忆。预期交互方式参考 ChatGPT 的 Memory Summary：用户查看摘要后，通过聊天或自然语言指令纠正系统的认识。

典型过程是：

```text
用户查看 Memory Summary
          │
          ▼
用户：“我的 NAS 已经换成 i5-6500”
          │
          ▼
系统识别这是对已有结论的纠正
          │
          ▼
定位受影响的底层记忆和相关来源
          │
          ▼
更新当前记忆状态并保留历史演化
          │
          ▼
重新生成 Memory Summary
```

用户显式纠正的权威性高于系统从普通聊天中自动推断出的结论。系统不应在没有充分证据的情况下，用后续弱推断静默覆盖用户已经明确确认的内容。

### 5.1 三种管理意图需要分开

虽然具体交互以后再设计，但方向上应区分三种不同语义：

- **纠正**：原结论不再准确，用新结论取代当前状态，同时保留必要历史。
- **不再主动提及**：限制后续使用，但不一定删除原始来源或历史事实。
- **删除**：用户要求移除相关记忆；是否同时处理原始来源和派生内容，需要后续定义清晰规则。

如果把这三种意图都实现成“删除摘要中的一句话”，系统将无法稳定满足用户预期。

### 5.2 歧义不能静默处理

当用户修改无法唯一对应某个结论时，系统不应擅自修改错误的记忆。

例如用户只说“不是 N100，是 i5-6500”，但历史里存在多台设备。系统需要结合上下文定位；仍无法判断时，应向用户确认具体对象。

## 六、来源解释是必要能力

Memory Summary 中的重要结论需要能够回到形成它的原始依据，至少在逻辑上保持可追溯关系。

来源解释主要服务：

- 用户判断系统为什么形成某个认识；
- 用户发现记忆错误时快速定位问题；
- 新旧结论冲突时进行判断；
- 删除或纠正时确定影响范围；
- 后续评估记忆抽取和整合质量。

“可解释来源”不意味着把所有原始聊天都直接展示给用户，也不意味着每个回答都必须展示引用。具体展示粒度后续设计，但内部不能在摘要生成后完全丢失来源关系。

## 七、更新时机与一致性方向

记忆形成和 Memory Summary 刷新不要求全部发生在对话主链路中。系统接受一定程度的延迟更新，以降低对正常对话延迟的影响，并为去重、冲突判断和摘要重建留下空间。

预期区分两类更新：

### 7.1 普通对话产生的隐式记忆

- 可以在后台延迟处理；
- 可以对相邻多轮对话进行合并后再判断；
- 不要求每轮对话都产生新记忆；
- 不要求每条记忆变化都立即重建摘要。

### 7.2 用户显式发起的记忆纠正

- 应进入更高优先级的处理路径；
- 系统应明确确认已经接受修改请求；
- 底层记忆状态应尽快反映用户的明确意图；
- Memory Summary 可以异步重建，但不能长期无提示地展示旧结论。

整体采用最终一致的方向，但需要让用户能够理解“修改已接受”和“摘要已刷新”之间可能存在短暂延迟。

## 八、已选择的方案组合

结合前期预研，本系统不采用单一方案，而采用以下组合：

### 8.1 核心：原子记忆集合 + 摘要投影

这是长期记忆的主干。内部维护可独立演化的记忆，Memory Summary 根据当前有效记忆生成。

### 8.2 结构化 Profile：只作为摘要组织方式，不作为唯一事实源

未来可以用结构化 Profile 或固定章节组织用户可见摘要，但它只是底层记忆的一种投影形式，不负责独立保存全部历史和来源。

### 8.3 分层 / 分域摘要：保留方向，暂不定义边界

当学习、偏好、项目经历等业务边界明确后，可以分别生成领域摘要，并在需要时形成更高层的全局摘要。当前不提前规定领域划分。

### 8.4 检索增强即时摘要：作为未来运行时能力

具体任务发生时，可以检索相关原子记忆和历史证据，临时形成任务上下文。它用于回答“本轮该想起什么”，不替代用户可见的稳定 Memory Summary。

### 8.5 单一滚动摘要：仅用于会话上下文压缩

滚动摘要仍可用于压缩单个长会话，但不作为跨会话长期记忆的事实源。

## 九、当前明确不做的决定

本阶段只确定方向，以下问题留到后续专题设计：

- 具体应该记住哪些信息；
- 记忆类型和业务领域如何划分；
- 全局摘要与各领域摘要的具体内容；
- 哪些信息需要在运行时检索；
- 记忆的数据库、索引和存储方案；
- 表结构、字段、API 和服务边界；
- 使用哪个模型以及如何设计抽取、整合和摘要 Prompt；
- 更新任务的调度、重试和并发机制；
- 用户界面和具体交互细节；
- 删除、保留期限、敏感信息和合规策略；
- 质量评估指标和测试数据集。

这些问题需要服从本文确定的核心语义，而不是反过来由某个数据库、框架或模型能力决定系统方向。

## 十、预期具备的系统性质

后续具体设计应至少满足以下性质：

1. **可重建**：Memory Summary 可以根据内部记忆重新生成。
2. **可演化**：新结论可以取代旧结论，但不会无故抹去必要历史。
3. **可纠正**：用户能够通过自然语言纠正系统对自己的认识。
4. **可追溯**：重要结论能够关联到形成它的原始依据。
5. **可区分意图**：纠正、抑制和删除具有不同语义。
6. **可延迟处理**：普通记忆形成不阻塞主要对话流程。
7. **可扩展**：未来增加分域摘要和任务相关检索时，不需要推翻底层记忆模型。
8. **摘要不等于全量记忆**：摘要保持可读，长尾信息由底层记忆和后续检索承载。
9. **原始内容不自动等于事实**：聊天和文件需要经过记忆形成过程，才能成为当前内部记忆的一部分。

## 十一、一句话设计定调

> algo-mentor 的记忆系统将采用“原始证据 → 可追溯原子记忆 → Memory Summary 管理视图”的主干架构，保留历史演化和来源关系，允许用户通过自然语言纠正记忆，并通过异步处理持续刷新摘要；分域摘要和任务相关检索在业务边界明确后逐步补充。
