# 记忆系统的定位与主流框架设计对比

更新时间：2026-07-06

## 核心结论

- **记忆系统不是"聊天上下文维护"**。滑动窗口式的上下文管理只是记忆系统里最浅的一层（短期/工作记忆），真正的记忆系统 = 短期上下文 + **跨会话的沉淀与召回** + **写入决策（什么值得记）** + **读取决策（什么该召回）**。
- 记忆系统的定位是**位于 LLM 之外的"状态层"**，用来补 LLM 先天无状态的缺陷，让一个失忆的模型表现得像"有状态、会积累、认识你"。它和数据库/缓存是同一类基础设施，而不是某个业务功能。
- 记忆系统的**价值全在两个决策上**：写什么、读什么。存储只是载体，谁都会做。
- 主流框架的设计可以分成三种范式：**上下文管理型**（Spring AI）、**认知分层型**（LangGraph/LangMem、HelloAgents）、**LLM 驱动的自动记忆型**（Mem0、Zep）。越往后越智能，也越重。
- 对 algo-mentor：以**应用层显式记忆**为主干，借"认知分层 + 生命周期"的抽象，存储走 **PostgreSQL + pgvector 单库**，暂不引入图数据库和 LLM 自动抽取管线。

## 一、到底什么是记忆系统

### 1.1 一组最容易混的概念

| 概念 | 是什么 | 类比人类 |
|---|---|---|
| **上下文窗口 Context Window** | 模型单次前向推理能"看到"的 token 总量，硬限制 | 此刻眼睛能看到的东西 |
| **对话历史 Chat History** | 把最近若干轮原样存下，下次拼进 prompt | 对刚才几句话的短暂印象 |
| **记忆系统 Memory System** | 独立于单次对话、能跨会话沉淀/组织/检索信息的子系统 | 长期记忆 + 回忆能力 |

一句话区分：

> **对话历史是"把原始数据留着"，记忆系统是"把有价值的信息提炼出来、存起来、需要时找回来"。**

### 1.2 为什么"滑动窗口"不算真正的记忆系统

把最近 N 轮原样塞进 prompt 的做法有三个致命特征：

1. **无提炼**：存的是原始流水，不是结论。用户 10 轮对话里透露"我在准备大厂算法面试、动态规划最弱"，滑动窗口只是把原文留着，并没有把这条**画像**抽出来。
2. **无跨会话**：窗口一滚出去就没了，换个会话从零开始。
3. **无检索**：只有"最近"这一个维度，没法按相关性把三个月前的关键信息捞回来。

所以它更准确的名字是**上下文管理 / 短期记忆**，是记忆系统里"工作记忆"那一层，但**不是记忆系统本身**。

### 1.3 记忆系统的定位（可操作定义）

> 记忆系统是一个位于 LLM 之外、独立的信息中枢。它在多次交互中主动地把有价值的信息**编码、存储、组织**，并在恰当时机**检索**出最相关的部分注入当前上下文，从而让无状态的模型表现得像有状态、会积累、认识你。

它的定位由四件事定义：

1. **它是"状态层"**：LLM 每次调用都失忆，记忆系统是外挂给它的持久状态，属于基础设施。
2. **核心动作是"写入决策"和"读取决策"**，不是"存"：写什么值得沉淀（importance / consolidate）、读什么该召回（相关性打分 / 时间衰减）。这两个决策决定记忆系统有没有用。
3. **对上层透明**：业务/模型不必关心信息存在哪、是什么类型，只管问"关于当前用户/问题，给我相关历史"。因此常被抽象成 `MemoryService` 或一个 tool——统一入口、隐藏内部结构。
4. **服务"跨时间的连续性"**：让用户感觉 AI 记得他、了解他、在陪他成长。对学习类产品，这几乎是产品价值的核心。

### 1.4 一张关系图

```
                  ┌─────────────────────────────┐
   一次请求  ───▶ │        LLM（无状态）         │ ───▶ 回复
                  └──────────▲──────────┬────────┘
              注入相关记忆    │          │  产生新信息
                            │          ▼
                  ┌─────────┴──────────────────────┐
                  │          记忆系统               │
                  │  写入决策(什么值得记) ──▶ 存储   │
                  │  读取决策(什么该召回) ◀── 组织   │
                  │  [工作/情景/语义…  分层与生命周期]│
                  └────────────────────────────────┘
```

上下文窗口/对话历史是"注入"这条线的下游，是记忆系统最浅的一层；记忆系统决定往窗口里塞什么、什么时候把旧信息重新拉回来。

## 二、主流框架怎么设计记忆系统

按"智能程度 / 复杂度"从轻到重排。

### 2.1 上下文管理型：Spring AI ChatMemory

Java 生态最主流、最轻的一档，本质就是 1.2 说的"滑动窗口 + 持久化"，**只解决短期记忆**。

- 核心是 `ChatMemory` 接口，默认实现 `MessageWindowChatMemory`：维护一个不超过 `maxMessages` 的消息窗口。
- 存储抽象成 `ChatMemoryRepository`：默认 `InMemoryChatMemoryRepository`，可换成 JDBC / Redis / Neo4j / Cassandra。JDBC 版对 PostgreSQL 等提供了 `Dialect` 和建表脚本。
- 通过 `MessageChatMemoryAdvisor` 自动把历史注入每次请求，用 `CONVERSATION_ID` 做会话隔离。
- 一个工程细节：1.1.x 起淘汰按"整轮"（turn）删除——一轮从 UserMessage 开始，含后续 assistant 回复、工具调用、工具结果，避免把一次工具调用链切断。所以 `maxMessages` 是上界，实际可能略少。

**定位**：把无状态 LLM 变成"这次对话不失忆"的有状态对话。**没有**提炼、跨会话画像、相关性召回。要长期记忆得自己在它之上叠一层。

### 2.2 认知分层型：LangGraph / LangMem、HelloAgents

借认知科学把记忆分成几类，每类不同生命周期与存储。这是目前**自研记忆系统最主流的心智模型**。

**LangGraph 的划分**（近乎业界通用词汇）：

- **短期记忆**：线程内（thread-scoped），是 agent state 的一部分，用 checkpointer 持久化，可断点续跑。
- **长期记忆**：跨会话，存进 `Store`，按 namespace（用户/应用）隔离，可配 embedding 做语义检索。长期记忆再分三类：
  - **语义记忆 Semantic**：事实/概念/用户画像与偏好——"用户是谁、知道什么"。
  - **情景记忆 Episodic**：具体事件与经历，常以 few-shot 形式沉淀"过去成功怎么处理"。
  - **程序性记忆 Procedural**：规则/技能，实践中体现为 system prompt、指令的迭代。
- 两种写入时机：**hot path**（对话中同步写，实时但增加延迟）与 **background**（后台异步提炼，不阻塞主链路）。`LangMem` SDK 就是专门做这三类记忆的抽取与管理。

**HelloAgents（教学框架）** 是同一范式的完整落地：工作记忆（TTL、纯内存）/ 情景记忆（SQLite+Qdrant）/ 语义记忆（Qdrant+Neo4j 知识图谱）/ 感知记忆（多模态）。亮点是把 **importance 权重、时间衰减打分、consolidate（短期→长期）、forget（重要性/时间/容量三策略）** 这套生命周期显式实现出来了。

> 注意 HelloAgents 一个关键区别：它把记忆封装成 `MemoryTool` 注册进工具体系，但其实战案例（PDF 学习助手）里**并没有让 LLM 自主调用**，而是应用代码在关键节点显式 `execute("add"/"search")`。即"注册成 tool"和"让模型自主调 tool"是两回事——它给了工具能力，实战用的是程序显式编排。详见下节 [三、埋点方式](#三两种埋点方式让模型自主-vs-程序显式)。

**定位**：提供"分层 + 生命周期"的骨架，长期记忆和短期上下文分开管理。是否引入图数据库/向量库是可选项，不是必需。

### 2.3 LLM 驱动的自动记忆型：Mem0、Zep

最智能也最重的一档：**用 LLM 自动决定"记什么、怎么更新"**，把 1.3 里的写入决策自动化。通常作为独立记忆服务/平台存在。

**Mem0（两阶段管线，2025）**：

- **抽取（Extraction）**：来一对新消息（user+assistant），结合"全局滚动摘要 + 最近 m 条消息"，让 LLM 抽出候选记忆（salient facts）。摘要由后台异步刷新，不阻塞主流程。
- **更新（Update）**：每条候选事实和向量库里 top-k 相似记忆比对，让 LLM 判定 **ADD / UPDATE / DELETE / NOOP**，从而自动去重、消解矛盾、更新旧事实。
- 变体 **Mem0ᵍ** 再加图数据库存实体和关系。
- 效果与代价：相比全量塞上下文，token 成本降 90%+、p95 延迟降 91%，LLM-as-Judge 提升约 26%。**代价是写入时每批候选都要一次路由 LLM 调用**，写入成本随对话轮数线性增长，与是否真有新信息无关。

**Zep / Graphiti（时序知识图谱，2025）**：

- 核心是 **Graphiti**：建在 Neo4j 上的**时序感知知识图谱**。关键创新是**双时间戳（bitemporal）**——每条关系同时记 event time（事实何时为真）和 ingestion time（何时被观测到），因此能无损处理"矛盾/被更新的事实"。
- 分层子图：episodic（原始数据）/ semantic（抽取的实体与关系）/ community（高层领域摘要），且 episode 与派生的语义边**双向索引**，可溯源引用——"非无损"检索。
- 检索：语义向量 + BM25 关键词 + 图遍历的混合检索，P95 约 300ms 且**检索期不调 LLM**。
- 代价：知识图谱的实现成本高于向量库——要定义本体（ontology）、维护 schema 一致性、建实体抽取管线；领域快速演化时僵化的本体会成为维护负担。

**定位**：把"写入/读取决策"尽量自动化，追求开箱即用的高质量长期记忆。适合不想自研、可接受外部依赖或专用存储的团队。

### 2.4 一张对比表

| 维度 | Spring AI ChatMemory | LangGraph / LangMem、HelloAgents | Mem0 | Zep / Graphiti |
|---|---|---|---|---|
| 范式 | 上下文管理 | 认知分层 | LLM 自动记忆（两阶段） | LLM 自动记忆（时序图谱） |
| 解决 | 短期不失忆 | 短期+长期分层 | 长期，自动提炼/更新 | 长期，时序推理+溯源 |
| 写入决策 | 无（原样存） | 半自动（importance/consolidate） | 全自动 LLM 抽取 | 全自动 LLM 抽取实体关系 |
| 更新/去重 | 无 | 手动 consolidate/forget | LLM ADD/UPDATE/DELETE/NOOP | 图的时序边失效（edge invalidation） |
| 存储 | JDBC/Redis/Neo4j… | 内存+向量库(+图库) | 向量库(+图库) | Neo4j 图库 |
| 检索期成本 | 无 LLM | 无 LLM（打分） | 无 LLM（向量） | 无 LLM（向量+BM25+图） |
| 写入期成本 | 极低 | 低 | 高（每批一次 LLM） | 高（抽取 LLM） |
| 生态 | Java/Spring | Python | Python/API | Python/API/服务 |
| 复杂度 | 低 | 中 | 中高 | 高 |

## 三、两种埋点方式：让模型自主 vs 程序显式

这是集成记忆时绕不开的一个正交选择，和上面的范式无关：

- **记忆作为 tool（模型自主调用）**：把 add/search 注册成工具，LLM 自己决定何时读写。适合开放式、交互不可预测的 agent（如自由对话）。代价：多一轮 LLM 决策、结果不确定、难覆盖测试、费 token。
- **应用层显式记忆（程序编排）**：业务代码在关键节点主动读写，记忆是**数据**不是 tool。适合流程可控、有明确埋点的产品。更可控、更省 token、更好测试。

HelloAgents 的实战、Spring AI、多数生产系统实际用的都是后者。前者只在真正开放的入口才划算。

## 四、对 algo-mentor 的选型建议

**结论：以应用层显式记忆为主干，借"认知分层 + 生命周期"抽象，存储走 PostgreSQL + pgvector 单库，暂不引入图数据库与 LLM 自动抽取管线。个别开放式入口（自由对话 AI 导师）再保留"记忆作为 tool"的能力。**

理由：

1. **核心场景流程可控**：刷题、AI 讲解、错题复盘、学习计划都是自定义业务动作，在哪写、写什么类型（这道题错了→情景；用户偏好某种讲法→语义）程序完全能决定。显式编排比让模型自主调 tool 更可控、省 token、好测试。
2. **借认知分层，别照搬重存储**：采用 工作/情景/语义 三类（暂不要感知记忆/多模态），配 importance + 时间衰减打分 + consolidate/forget 生命周期——这些是 LangGraph/HelloAgents 里真正值钱的抽象。
3. **存储用 PG + pgvector**：一个库同时装"结构化记忆表 + 向量语义检索"，与既定单库 + Flyway 路线一致，省掉 Qdrant/Neo4j 一整套外部依赖。真遇到向量规模瓶颈再引专用库。
4. **Mem0/Zep 的思想选择性吸收**：写入去重可以借鉴 Mem0 的 ADD/UPDATE/DELETE 语义（但先用规则实现，别一上来就每次调 LLM）；"用户偏好会随时间变化"可借鉴 Zep 的"新事实使旧事实失效"，但用一个 `valid_until` 字段就够，不必上时序图谱。
5. **封装为 `MemoryService`**：清晰的 service/client 边界，隐藏"存 PG 还是向量、哪类记忆"，对上层只暴露"写入 / 召回"。符合项目对 AI 能力封装的约定。

一句话：**借它们的"记忆分层 + 生命周期"，弃"重存储 + 多模态 + 每次调 LLM 的自动记忆"，落到 Spring + pgvector 的应用层显式记忆上。**

## 五、可继续深入 / 横向扩展的方向

- **写入时机**：hot path（同步写，实时但增延迟）vs background（异步提炼，不阻塞），以及二者混合。
- **记忆的更新与消解矛盾**：Mem0 的 ADD/UPDATE/DELETE/NOOP 路由、Zep 的 bitemporal 边失效，如何用关系型字段低成本模拟。
- **遗忘策略**：重要性 / 时间衰减 / 容量 / 访问频率的加权"智能遗忘"，以及敏感信息的彻底删除（向量库/图库残留问题）。
- **记忆与 RAG 的边界与协作**：记忆=关于"用户和交互历史"，RAG=关于"外部知识库"，何时用哪个、如何做智能路由。见 [[RAG阶段1流程全貌复习笔记]]。
- **上下文注入与工具结果**：召回的记忆如何注入 prompt、和工具结果一样面临"原文/摘要/引用"的取舍。见 [[智能体跨轮次上下文中的工具结果设计]]。
- **多用户数据隔离**：namespace / user_id 级隔离在 PG + pgvector 下的实现与检索性能。
